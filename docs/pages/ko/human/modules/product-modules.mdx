# Product Modules

product module은 platform이 호스팅하는 업무용 surface다. 같은 module contract를
공유하지만, 각 module은 자기 작업에 맞는 storage substrate와 interface를 고른다.

## Built or Started

- `document`는 QMDB 위에 block-based document를 저장하고 QMDB state sync를
  노출한다.
- `forge`는 git-backed project state를 저장하고, git head에서 root를 계산하며
  connectivity verification으로 pack install을 보호한다.
- `chat`은 storage를 소유하는 chat module이다: channel, thread, edit, reaction,
  membership을 entity당 QMDB record 하나로 저장하고, 구독한 module로 hook
  fan-out을 보낸다.
- `agent`는 agent registry, channel watch, run record를 담는 순수 state
  machine이다.
- `tasks`는 staged write 위의 작은 canonical task list를 저장한다.
- `vaults`는 owner-gated write로 opaque secret ciphertext를 복제한다.
- `inbox`는 follow-up op로 배달되는 per-member notification queue를 저장한다.
- `automations`는 chat hook seam 위에서 도는 operator-defined rule을 저장한다.
- `files`는 duckfs다: consensus-replicated, copy-on-write, content-addressed
  filesystem — 모든 node가 모든 byte를 들고 있고, byte는 restart를 견딘다.
- `jobs`는 first-claim-wins claim을 쓰는 consensus-native work board다.
- `kv`, `valset`, `saga`, `governance`, `directory`, `greeter`는 infrastructure,
  example, test를 지원한다.

## Inbox

inbox는 per-member notification queue를 consensus state로 담는다: member마다
seq가 붙은 item list와 read cursor 하나씩이다. write는 `Deliver`, `MarkRead`,
`Clear`로, read는 `List`, `Unread`로 간다. cap은 execute에서 rejection으로
강제된다(`kind` 64바이트, `body` 16 KiB, bounded member 수). 예외 하나가
의도적이다: per-member item cap을 넘는 delivery는 가장 오래된 item을
deterministic하게 drop한다 — 이것은 notification queue지 ledger가 아니다.

핵심 mechanism은 atomic-with-cause delivery다. 다른 module이 notification을
follow-up op로 배달하므로, notification은 그 원인이 된 event와 같은 block에서
commit된다(platform promise P2). external push service는 없다 — queue 자체가
delivery이고, 이것이 air-gap-native notification story다. 각 item의 `source`는
배달한 origin을 기록한다 — module id, external submitter는 `ext:` + lowercase
hex, 또는 `system` — module이 직접 계산하며 caller가 공급하지 않는다.

## Automations

automations는 operator-defined rule을 저장한다 — chat post filter 위의
trigger와, chat message를 post하거나 task를 만드는 action — 그리고 bounded
run-history ring을 함께 둔다. rule 관리는 `CreateRule`, `SetEnabled`,
`DeleteRule`로, read는 `ListRules`, `GetRule`, `RunHistory`로 간다. hook
event는 origin-gated다: `Origin::Module("chat")`만 hook arm에 도달하므로
submitter가 hook event를 위조할 수 없다.

rule은 post author가 user일 때만 발화한다. module이나 agent가 작성한 post —
이 module 자신의 follow-up 포함 — 는 rule을 절대 trigger하지 않으므로, hooked
channel에 post하는 automation이 cascade할 수 없다. event당 action budget은
8이고, 모든 action은 emit 전에 probe된다: host-routed query로 target channel이
존재하는지, 합성된 message/task id가 미사용인지 검증한다 — user가 합성 id를
먼저 post해서 rule을 막아버리는 id-squatting을 차단한다. probe 실패나
message-text fetch 실패는 block을 abort하는 대신 `action_ok = false`인 run
record로 강등된다. probe가 볼 수 없는 것은 여전히 trigger한 post와 하나의
atomic unit으로 commit되거나 abort된다(P2).

## Files

files는 duckfs다: consensus-replicated, copy-on-write, content-addressed
filesystem. 모든 node가 모든 byte를 consensus state로 들고 있다 — byte는
block을 타고 이동하며 restart를 견딘다. 그래서 commit된 file은 어느 node에서든
읽을 수 있다. chunk를 마침 들고 있던 node에 묶인 promise가 아니다. state는
둘로 나뉜다: immutable object store(chunk, file, tree, snapshot — 전부
content-addressed)와 작은 mutable refs cell(live head, pin table, bounded
history window, staging table, watch set)이다. root는 refs cell만 hash하고,
tree 전체에는 transitively commit한다. writable root 둘이 authority를
gate한다: `/home/<owner>/**`는 origin에서 유도된 owner 본인만,
`/shared/**`는 아무 member나 쓸 수 있다. read는 어디서든 cluster-visible하다 —
`/home`은 write만 gate한다.

write는 stage하고 commit한다. `PutBlob`은 raw chunk 하나를 stage한다(binary op
frame이고, owner별 quota가 걸리며, 참조되지 않으면 deterministic하게
만료된다). `Commit`이 atomic unit이다 — path change 묶음(`Put`, `Mkdir`, `Rm`,
`Mv`, `Symlink`)이 base snapshot에 대한 per-path compare-and-swap 아래
들어간다: 바뀐 모든 path는 base와 live head 사이에서 untouched여야 하고,
아니면 commit 전체가 reject된다. 그래서 겹치지 않는 동시 commit은 false
conflict 없이 interleave되고, 겹치는 commit은 소리 내며 실패한다. 성공한
commit은 immutable snapshot을 append하고 — copy-on-write라서 바뀌지 않은
subtree는 version 간에 hash로 공유된다 — head를 전진시키며, 구독한 module로
watch notification을 같은 block에서 fan-out한다(P2). `Pin`과 `Unpin`은 named
snapshot을 bounded history window 너머까지 살려둔다. cap은 execute에서
rejection으로 강제되어 oversized value가 root preimage에 들어가지 않는다.

read는 snapshot-addressable한 순수 함수다: `Stat`, `Ls`, `Read`(byte-range),
`Find`, `Grep`, `History`, `Diff`, `Refs` — 각각 cursor-paged이고 head에서든
resolvable한 아무 snapshot에서든 답한다. duckfs는 agent memory이기도 하다 —
삭제된 `memory` module을 흡수했고, memory가 immutable generation으로 하던 일을
duckfs는 snapshot으로 한다. agent workspace는 `/home`과 `/shared` 아래의
평범한 file이다. `Grep` hit는 인용 가능한
`duck://files/<path>@<snapshot>#L<line>` evidence URI를 담고, per-file meta는
`kind=skill` 같은 convention을 지원하며(shared skill은 `/shared/skills/` 아래
산다), segment 단위로 match하는 prefix watch(`/a`는 `/a/b`에 match하고
`/ab`에는 절대 match하지 않는다)가 어느 module에든 trigger한 commit과
atomic하게 배달되는 change notification을 준다.

## Jobs

jobs는 on-platform actor를 위한 consensus-native work board다: 사람과 agent
fleet이 평범한 signed op를 제출한다. submitter가 job을 올리면 아무 worker나
claim할 수 있고, consensus order로 정확히 하나의 claim만 이긴다 — total order가
곧 lock이고, 진 claim은 모든 node에서 소리 내며 block을 fail한다. 그 rejection이
race-resolution signal이다. lifecycle은 submit에서 pending으로, claim에서 view
lease 아래 processing으로, 그리고 done 또는 failed로 finalize된다. write는
`Submit`, `Claim`, `Finalize`, `Release`, `Reclaim`, `Cancel`, `Prune`,
`RegisterWorker`, `UnregisterWorker`로, read는 `Get`, `List`, `Counts`로 가며
committed state에서만 답한다.

claim의 view lease가 만료되면 누구든 job을 `Reclaim`해 pending으로 되돌릴 수
있다 — reclaim은 permissionless다. attempt는 8회로 cap되고, `Cancel`과
`Prune`은 submitter 전용이다. jobs는 saga와 구별된다: jobs는 signed RPC op로
행동하는 actor를 위한 product work board이고, saga는 node 자신의 worker loop가
수행하는 off-consensus 작업을 위한 platform의 reactor-effect ledger다. jobs는
saga도 reactor도 절대 건드리지 않는다.

worker는 genesis config가 아니라 consensus state다. worker module은 module-origin
follow-up으로 jobs에 `RegisterWorker`를 보내 자기 자신만 등록한다. external과
system origin은 임의의 worker를 지정할 수 없고, worker set은 16개로 cap된다.
성공한 `Submit`마다 같은 block 안에서 등록된 worker별 `JobsEvent::Submitted`
follow-up 하나를 emit한다. 이 fan-out도 host의 block dispatch budget을 소모한다.

**Cascade rule:** 이 slice는 주어진 job kind에 대해 claim하는 worker가 하나인
모드를 지원한다. 등록된 worker 둘이 submit cascade 안에서 같은 job을 모두
claim하면, 두 번째 `Claim`은 첫 번째 staged claim을 보고 reject하며 P2에 따라
전체 submit block을 abort한다. `MAX_WORKERS`는 나중의 off-cascade 전략을 위한
상한이지, 같은 kind를 여러 worker가 in-cascade로 claim하라는 뜻이 아니다.

## Interface Shape

interface crate는 module-specific payload를 encode/decode하고, host는 opaque byte만
route한다. product module은 implementation API가 아니라 typed message와 query를
공유한다.

## Product Pressure

checked-in module에서 유용한 pressure point가 보인다. chat은 QMDB-backed
channel storage 위의 live product read를 검증하고, forge는 authenticated
project state를 검증하며, module wave — inbox, automations, files, jobs — 는
follow-up atomicity, hook fan-out, 그리고 앞으로의 collaboration 기능이 기댈
snapshot history를 가진 fully replicated consensus byte를 검증한다.
