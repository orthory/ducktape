# Product Modules

product module은 platform이 호스팅하는 업무용 surface다. 같은 module contract를
공유하지만, 각 module은 자기 작업에 맞는 storage substrate와 interface를 고른다.

## Built or Started

- `pages`는 QMDB 위에 nested block page, page tab, comment thread를 저장하고
  QMDB state sync를 노출한다.
- `forge`는 git-backed project state를 저장하고, git head에서 root를 계산하며
  connectivity verification으로 pack install을 보호한다.
- `chat`은 storage를 소유하는 chat module이다: channel, thread, edit, reaction,
  membership을 entity당 QMDB record 하나로 저장하고, 구독한 module로 hook
  fan-out을 보낸다.
- `agent`는 agent registry, channel watch, run record를 담는 순수 state
  machine이다.
- `tasks`는 staged write 위의 작은 canonical task list를 저장한다.
- `vaults`는 owner-gated write로 opaque secret ciphertext를 복제한다.
- `inbox`는 follow-up op로 배달되는 per-member notification queue를 저장한다.
- `automations`는 chat hook seam 위에서 도는 operator-defined rule을 저장한다.
- `files`는 duckfs다: consensus-replicated, copy-on-write, content-addressed
  filesystem — 모든 node가 모든 byte를 들고 있고, byte는 restart를 견딘다.
- `jobs`는 first-claim-wins claim을 쓰는 consensus-native work board다.
- `identity`는 member key, display name, bound node를 한 AccountId 아래 두는
  canonical account registry다.
- `duckdns`는 선택적인 `<handle>.duck` → AccountId 이름만 더한다. node,
  service, route directory는 소유하지 않으며 workspace identity는 이름 등록을
  요구하지 않는다.
- `kv`, `valset`, `saga`, `governance`, `directory`, `greeter`는 infrastructure,
  example, test를 지원한다.

## Chat And Huddles

chat은 channel, message thread, edit, reaction, membership, hook fan-out을
소유한다. hot channel이 commit bomb이 되지 않도록 whole-history value 하나가
아니라 entity당 QMDB record 하나를 저장하고, computed key로 page한다.

huddle은 chat channel에 붙는다. consensus는 `join_huddle`, `leave_huddle`,
`sweep_huddle`로 roster만 저장한다. mute, camera, peer beacon 같은 media state는
ephemeral이다. live node에는 typed call socket과 voice/video hub가 있다. audio와
control은 voice lane을 타고, camera fragment는 별도 video lane을 타며, app은 docked
또는 popped-out huddle card를 렌더링한다. 현재 admission은 local-live-flow 기반이고,
roster-derived media admission은 남은 security hardening seam이다.

## Pages

pages는 block editor module이다. page root, nested page parent, block, comment
thread를 같은 QMDB-backed module에 저장하므로 page content와 comment가 함께
state-sync된다. write는 `CreatePage`, `SetPageParent`, `DeletePage`,
`InsertBlock`, `UpdateText`, `SetKind`, `SetChecked`, `MoveBlock`, `RemoveBlock`,
`AddComment`, `EditComment`, `DeleteComment`, `ResolveThread`로 간다. read는 page와
block lookup, page list, page 또는 visible block set의 comment-thread query를
포함한다.

UI도 같은 형태를 따른다: nested page tree, `openTabs` 기반 page tab,
focus-light block editing, block별 comment affordance, 오른쪽 comments panel.
comment는 현재 plain text이고 별도 `comments` crate가 아니라 `pages` 안에 산다.
이것이 이전 redesign plan과 다른 구현 결과다.

## Agents And Runs

agent stack은 의도적으로 나뉘어 있다. `agent`는 registry다: display name, executor
requirement, prompt pin, permission, status, watch, run record를 담는다. `runs`는
chat context로 prompt를 compose하고, dispatch recipe를 submit하고, response를
record하며, channel을 watch하고, jobs board에 opt in할 수 있다. `dispatch`와
`saga`는 capability-routed execution과 strict lease를 소유하므로 model output은
숨은 local state가 아니라 ordered data로 돌아온다.

node는 operator spec에서 local capability provider를 discover하고, truthful tag set을
`capability` module에 announce하며, 자기 key에 assign된 lease만 dispatch worker로
실행한다. console은 이 상태를 다시 join한다. member row는 announced executor tag를
보여주고, agent form은 registry-backed **Runs on** picker를 쓰며, in-flight run은
saga lease를 잡은 node를 표시할 수 있다.

## Inbox

inbox는 per-member notification queue를 consensus state로 담는다: member마다
seq가 붙은 item list와 read cursor 하나씩이다. write는 `Deliver`, `MarkRead`,
`Clear`로, read는 `List`, `Unread`로 간다. cap은 execute에서 rejection으로
강제된다(`kind` 64바이트, `body` 16 KiB, bounded member 수). 예외 하나가
의도적이다: per-member item cap을 넘는 delivery는 가장 오래된 item을
deterministic하게 drop한다 — 이것은 notification queue지 ledger가 아니다.

핵심 mechanism은 atomic-with-cause delivery다. 다른 module이 notification을
follow-up op로 배달하므로, notification은 그 원인이 된 event와 같은 block에서
commit된다(platform promise P2). external push service는 없다 — queue 자체가
delivery이고, 이것이 air-gap-native notification story다. 각 item의 `source`는
배달한 origin을 기록한다 — module id, external submitter는 `ext:` + lowercase
hex, 또는 `system` — module이 직접 계산하며 caller가 공급하지 않는다.

## Automations

automations는 operator-defined rule을 저장한다 — chat post filter 위의
trigger와, chat message를 post하거나 task를 만드는 action — 그리고 bounded
run-history ring을 함께 둔다. rule 관리는 `CreateRule`, `SetEnabled`,
`DeleteRule`로, read는 `ListRules`, `GetRule`, `RunHistory`로 간다. hook
event는 origin-gated다: `Origin::Module("chat")`만 hook arm에 도달하므로
submitter가 hook event를 위조할 수 없다.

rule은 post author가 user일 때만 발화한다. module이나 agent가 작성한 post —
이 module 자신의 follow-up 포함 — 는 rule을 절대 trigger하지 않으므로, hooked
channel에 post하는 automation이 cascade할 수 없다. event당 action budget은
8이고, 모든 action은 emit 전에 probe된다: host-routed query로 target channel이
존재하는지, 합성된 message/task id가 미사용인지 검증한다 — user가 합성 id를
먼저 post해서 rule을 막아버리는 id-squatting을 차단한다. probe 실패나
message-text fetch 실패는 block을 abort하는 대신 `action_ok = false`인 run
record로 강등된다. probe가 볼 수 없는 것은 여전히 trigger한 post와 하나의
atomic unit으로 commit되거나 abort된다(P2).

## Files

files는 duckfs다: consensus-replicated, copy-on-write, content-addressed
filesystem. 모든 node가 모든 byte를 consensus state로 들고 있다 — byte는
block을 타고 이동하며 restart를 견딘다. 그래서 commit된 file은 어느 node에서든
읽을 수 있다. chunk를 마침 들고 있던 node에 묶인 promise가 아니다. state는
둘로 나뉜다: immutable object store(chunk, file, tree, snapshot — 전부
content-addressed)와 작은 mutable refs cell(live head, pin table, bounded
history window, staging table, watch set)이다. root는 refs cell만 hash하고,
tree 전체에는 transitively commit한다. writable root 둘이 authority를
gate한다: `/home/<owner>/**`는 origin에서 유도된 owner 본인만,
`/shared/**`는 아무 member나 쓸 수 있다. read는 어디서든 cluster-visible하다 —
`/home`은 write만 gate한다.

write는 stage하고 commit한다. `PutBlob`은 raw chunk 하나를 stage한다(binary op
frame이고, owner별 quota가 걸리며, 참조되지 않으면 deterministic하게
만료된다). `Commit`이 atomic unit이다 — path change 묶음(`Put`, `Mkdir`, `Rm`,
`Mv`, `Symlink`)이 base snapshot에 대한 per-path compare-and-swap 아래
들어간다: 바뀐 모든 path는 base와 live head 사이에서 untouched여야 하고,
아니면 commit 전체가 reject된다. 그래서 겹치지 않는 동시 commit은 false
conflict 없이 interleave되고, 겹치는 commit은 소리 내며 실패한다. 성공한
commit은 immutable snapshot을 append하고 — copy-on-write라서 바뀌지 않은
subtree는 version 간에 hash로 공유된다 — head를 전진시키며, 구독한 module로
watch notification을 같은 block에서 fan-out한다(P2). `Pin`과 `Unpin`은 named
snapshot을 bounded history window 너머까지 살려둔다. cap은 execute에서
rejection으로 강제되어 oversized value가 root preimage에 들어가지 않는다.

read는 snapshot-addressable한 순수 함수다: `Stat`, `Ls`, `Read`(byte-range),
`Find`, `Grep`, `History`, `Diff`, `Refs` — 각각 cursor-paged이고 head에서든
resolvable한 아무 snapshot에서든 답한다. duckfs는 agent memory이기도 하다 —
삭제된 `memory` module을 흡수했고, memory가 immutable generation으로 하던 일을
duckfs는 snapshot으로 한다. agent workspace는 `/home`과 `/shared` 아래의
평범한 file이다. `Grep` hit는 인용 가능한
`duck://files/<path>@<snapshot>#L<line>` evidence URI를 담고, per-file meta는
`kind=skill` 같은 convention을 지원하며(shared skill은 `/shared/skills/` 아래
산다), segment 단위로 match하는 prefix watch(`/a`는 `/a/b`에 match하고
`/ab`에는 절대 match하지 않는다)가 어느 module에든 trigger한 commit과
atomic하게 배달되는 change notification을 준다.

client 절반은 OS-side checkout/commit engine(`crates/duckfs/client`)과
`ducktape-fs` CLI다. checkout은 duckfs subtree를 실제 working directory로
materialize하고 그 옆에 `.duckfs/index.json`을 둔다 — git의 index discipline:
working copy가 내려온 base snapshot, 대화하는 node, 그리고 per-path
hash/size/mtime record. `ducktape-fs`는 read verb(`ls`, `cat`, `stat`,
`history`, `diff`)과 working-copy loop(`checkout`, `status`, `commit`, `pin`)을
갖는다. engine은 모든 object를 client-side에서 hash하고 이름 붙이며(validator가
derive하는 것과 byte-identical), cluster에 없는 chunk만 stage하고, 하나의 atomic
`Commit`을 submit한다. conflict 처리는 구조적으로 안전하다: CAS rejection에서
engine은 겹치지 않는 upstream 작업만 auto-rebase하고(절대 silent merge가 아니다),
겹치는 edit에는 structured conflict report를 낸다(single daemon 기준; multi-validator
cluster에서는 module의 reason string이 consensus finalization을 넘어 살아남지 못해
지금은 overlap을 평범한 rejection으로 보고한다). workspace RPC(`POST /v1/fs/workspaces`,
`.../commit`, `DELETE`)는 jobs/sandbox seam이다: daemon이 자기 root 아래에서
checkout을 관리하며 같은 engine을 actor lane으로 구동하므로 self-dial 없이 job이
disk의 file을 편집하고 commit할 수 있다. `ducktape-fs mount <prefix> <dir>`는
duckfs subtree를 실제 kernel filesystem으로 내세운다 — `fuse` cargo feature 뒤에
있고(unprivileged, `fusermount3` 경유 — default build은 libfuse가 필요 없고 verb를
"`--features fuse`로 rebuild하라"는 분명한 error로 남긴다). 기본은 read-only로,
sync `NodeApi` 위에서 한 번 resolve해 mount 수명 동안 PIN한 snapshot을 serve한다 —
stable하고 reproducible한 view이며, immutable한 content라 강하게 cache한다(lazy
`ls`/`stat` inode table + bounded read-through block cache). read는 움직이는 head를
절대 보지 않으므로, 새 commit을 보려면 remount한다. `--rw`는 REAL working copy를
내세운다 — 숨겨진 `<dir>.duckfs-backing` 디렉터리로 checkout해 passthrough로 serve
한다 — 그리고 write는 commit할 때만 cluster truth가 된다: 기본은 명시적(unmount
시 commit 방법을 출력하고, 아무것도 자동으로 land하지 않는다), 또는 `--auto-commit N`
으로 dirty할 때 N초마다 commit한다(겹치지 않는 upstream 작업은 auto-rebase; 진짜
conflict는 크게 log하고 mount는 계속 serve한다 — silent merge 없음, write drop
없음). SIGINT/SIGTERM은 깔끔하게 unmount한다. 문서화된 non-goal: cross-node lock/mmap
coherence 없음; uid/gid/mode는 synthetic(단 size, mtime, exec bit은 `--rw`에서
passthrough된다); case-insensitive host에서는 case가 충돌하는 sibling 이름을
materialize할 수 없다; crash는 stale mountpoint를 남기며 `fusermount3 -u <dir>`로
복구한다.

## Jobs

jobs는 on-platform actor를 위한 consensus-native work board다: 사람과 agent
fleet이 평범한 signed op를 제출한다. submitter가 job을 올리면 아무 worker나
claim할 수 있고, consensus order로 정확히 하나의 claim만 이긴다 — total order가
곧 lock이고, 진 claim은 모든 node에서 소리 내며 block을 fail한다. 그 rejection이
race-resolution signal이다. lifecycle은 submit에서 pending으로, claim에서 view
lease 아래 processing으로, 그리고 done 또는 failed로 finalize된다. write는
`Submit`, `Claim`, `Finalize`, `Release`, `Reclaim`, `Cancel`, `Prune`,
`RegisterWorker`, `UnregisterWorker`로, read는 `Get`, `List`, `Counts`로 가며
committed state에서만 답한다.

claim의 view lease가 만료되면 누구든 job을 `Reclaim`해 pending으로 되돌릴 수
있다 — reclaim은 permissionless다. attempt는 8회로 cap되고, `Cancel`과
`Prune`은 submitter 전용이다. jobs는 saga와 구별된다: jobs는 signed RPC op로
행동하는 actor를 위한 product work board이고, saga는 node 자신의 worker loop가
수행하는 off-consensus 작업을 위한 platform의 reactor-effect ledger다. jobs는
saga도 reactor도 절대 건드리지 않는다.

worker는 genesis config가 아니라 consensus state다. worker module은 module-origin
follow-up으로 jobs에 `RegisterWorker`를 보내 자기 자신만 등록한다. external과
system origin은 임의의 worker를 지정할 수 없고, worker set은 16개로 cap된다.
성공한 `Submit`마다 같은 block 안에서 등록된 worker별 `JobsEvent::Submitted`
follow-up 하나를 emit한다. 이 fan-out도 host의 block dispatch budget을 소모한다.

**Cascade rule:** 이 slice는 주어진 job kind에 대해 claim하는 worker가 하나인
모드를 지원한다. 등록된 worker 둘이 submit cascade 안에서 같은 job을 모두
claim하면, 두 번째 `Claim`은 첫 번째 staged claim을 보고 reject하며 P2에 따라
전체 submit block을 abort한다. `MAX_WORKERS`는 나중의 off-cascade 전략을 위한
상한이지, 같은 kind를 여러 worker가 in-cascade로 claim하라는 뜻이 아니다.

## Identity

identity는 canonical account registry다(`crates/system/identity`). account는
founding member key에서 정해진 stable AccountId, 여러 scheme의 member key,
공유 display name과 replay nonce, 그리고 여러 bound node key를 가진다. node는
계속 workspace의 mesh/valset identity이므로, 여러 device와 node가 한 account에
속해도 network identity 자체가 합쳐지지는 않는다.

`BindNode`는 SUBMIT하는 node(검증된 origin이며 절대 payload field가 아니다)를
authorizing member key의 account에 bind한다. member proof는
chain-id ‖ node-key ‖ nonce preimage를 덮으므로 다른 network, node, nonce로
replay할 수 없다. 아직 어느 account에도 속하지 않은 새 member key는 첫 bind에서
account를 만든다. networked node에서는 submit node가 현재 validator 또는
resident여야 한다. `UnbindNode`는 account의 살아남은 아무 member key나
authorize할 수 있고, `AddMemberKey`는 기존 member의 동의와 새 key의 possession
proof를 모두 요구하며, `RemoveMemberKey`는 마지막 live member를 보존한다.
member-signed 변경이 accept될 때마다 shared nonce가 증가한다. 마지막 node를
unbind해도 account, member key, name, nonce는 남으므로 나중의 bind는 같은
identity로 resolve된다.

`SetAccountName`은 origin-gated일 뿐이다(bound node는 신뢰된
hardware이므로 member-key signature가 필요 없다): submit하는 node가 bound된
account의 display name을 64바이트 한도로 설정하며, nonce는 bump하지 않는다 —
member-key signature를 소비하지 않기 때문이다.

bind는 per-node로 남는 것들을 바꾸지 않는다: mesh tracking, valset seat,
quorum arithmetic은 이 module의 영향을 받지 않는다. validator 셋을 굴리는
account는 여전히 세 자리를 차지하고 세 표를 던진다 — identity는 authority,
display, authorship resolution을 위해 node를 account에 매핑할 뿐 consensus
weight를 합치지 않는다.

identity가 없던 network에 이를 추가하는 것은 다른 module-set 변경과
마찬가지다: genesis app-hash가 옮겨가므로, 이미 돌고 있는 network가 이를
적용하려면 coordinated rebuild — rolling이 아닌, 모든 validator에 걸친
lockstep upgrade — 가 필요하다.

이 module은 public membership과 binding state만 저장한다. private member key의
custody는 그 위에 얹힌 desktop-app의 관심사이며 `bin/node`의 `user-key` verb를
통해 다룬다. primary native member의 24-word mnemonic은 raw ed25519 seed를
그대로 encoding한 것이라 — entropy를
보존하고 identity를 보존한다 — 새 identity를 derive하는 게 아니라 정확히 같은
identity를 복구한다. password는 local encryption 용도일 뿐이다 — argon2id가
key를 만들고 그 key로 XChaCha20-Poly1305가 seed를 at rest 상태로 암호화한다 —
key derivation에는 전혀 관여하지 않으므로, password를 잊어도 mnemonic으로
복구한 뒤 새 password를 설정하면 그만이다. node key는 의도적으로 이런 처리를
전혀 받지 않는다: plaintext로 남고 disposable하다 — consensus가 매 view마다
node key로 서명하고, boot이 password prompt에 막혀서는 안 되기 때문이다.
잃어버리거나 탈취된 device의 복구 경로는 unbind 후 rejoin이고, node key의
at-rest 보호는 OS full-disk encryption이 문서화된 답이다.

## Interface Shape

interface crate는 module-specific payload를 encode/decode하고, host는 opaque byte만
route한다. product module은 implementation API가 아니라 typed message와 query를
공유한다.

## Product Pressure

checked-in module에서 유용한 pressure point가 보인다. chat은 QMDB-backed
channel storage 위의 live product read를 검증하고, forge는 authenticated
project state를 검증하며, module wave — inbox, automations, files, jobs — 는
follow-up atomicity, hook fan-out, 그리고 앞으로의 collaboration 기능이 기댈
snapshot history를 가진 fully replicated consensus byte를 검증한다.
