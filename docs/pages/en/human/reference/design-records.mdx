## Historical Material

Implementation plans are not maintained as product documentation after the code
ships. The durable parts move into Vocs pages, ADRs, or the module comments and
tests that now prove the behavior.

This pass prunes shipped step-by-step plans for pages/comments, agent visibility,
agent setup simplification, chat polish, huddle pop-out, video calls, and the
node-upgrade implementation plan. It also removes historical root-cause/spec
notes for the admission-boundary fork and restart recovery now that those facts
are covered by Vocs and checked-in tests. The maintained facts now live in:

- [Product Modules](/en/human/modules/product-modules) for pages, comments,
  agents, jobs, and the module wave;
- [Implementation Status](/en/human/reference/implementation-status) for what is
  checked in and tested;
- [Node Upgrades](/en/human/network/node-upgrades) and
  [agent upgrade operations](/en/agent/network/node-upgrades) for the upgrade
  policy and runbook;
- the ADRs listed above for decisions that should outlive the implementation
  branch.

## Housekeeping Rules

- Put maintained reader docs under `docs/pages` so Vocs can build and index
  them.
- Keep ADRs when they capture a decision boundary, not a task checklist.
- Keep runbooks when an operator still executes them.
- Delete or fold implementation plans once the code, tests, and Vocs summaries
  supersede them.
