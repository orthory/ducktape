## Ordered Delivery

QMDB roots are operation-log commitments. The same final key-value set can have
different roots when produced by different write orders. Ducktape therefore
cannot rely on eventual arrival order. Validators must apply the same agreed
sequence.

`OrderedNode` is the seam between the host and an `Orderer`. Finalized ops are
drained in view order, and the host receives an explicit `BlockContext` derived
from that finalized view.

## Commonware Simplex

The consensus crate contains the commonware Simplex-backed orderer. Its current
responsibilities include:

- content-addressed ingest, with payload bytes re-hashed on receipt;
- eager payload gossip through the relay path;
- view-keyed finalized release through the inbox;
- resolver fetch for late joiners and missing payloads;
- scheme documentation around V1 ed25519 and future rekey/respawn behavior.

Malformed finalized ops are deterministic no-ops from the consensus perspective:
the host rejects or rolls them back without halting honest nodes.

## Node Paths

The repository contains two node styles:

- `Node<T>` is the earlier loopback transport seam for local convergence.
- `OrderedNode<O>` is the ordered lane that applies consensus-finalized ops.

The real-socket binary under `bin/node` drives `OrderedNode<SimplexOrderer>` over
commonware networking. The two-process demo proves two OS processes can converge
on one app-hash over TCP plus Simplex.
