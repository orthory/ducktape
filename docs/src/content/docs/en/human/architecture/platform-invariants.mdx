Ducktape is built around five invariants. They are not style preferences; they
are the rules that let independent validators derive the same root-hash from the
same agreed operation order.

## Isolation

A product module is a crate that implements `sdk::Module`. It normally depends
only on `sdk` and the crate-root wire types of modules it talks to.
The host sees a module id, an `execute` entry point, optional read projections,
commit/abort hooks, and `root() -> StateRoot`.

Modules never call another module implementation directly. Reads use
`Ctx::query` or `Ctx::module_root`. Writes are emitted as `Msg` intents and
re-dispatched by the host as local follow-ups.

## Determinism

Everything between consensus delivery and `root()` is a deterministic function
of the agreed op order. The state machine uses agreed height/time, sorted maps,
and explicit byte payloads. Wall clock, random choices, network IO, LLM calls,
and external fetches do not run inside module execution.

## Host-Lent Atomicity

Modules stage writes during `execute`. The host owns the block boundary: on a
clean drain it calls `commit_block` for every touched module; on any error or
dispatch-budget breach it calls `abort_block`. A failed block leaves module
roots unchanged.

## Root-Hash Commits to Everything

Every durable state that matters must sit under a module root. The global root is
a sorted hash over `(module_id, module_root)` pairs. QMDB roots, forge's git-head
root, and canonical in-memory snapshots all compose the same way.

## Single-Store Step

A deterministic step writes one store. Cross-store work is sequenced through
follow-up messages or through the saga/worker pattern. That keeps the current
design away from two-phase commit while the host still provides block-level
atomicity.
