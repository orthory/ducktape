The repository currently has three separate network and membership concerns:
message propagation, ordered consensus delivery, and validator membership state.

Related: [Coordination](/en/human/network/coordination) covers rendezvous and
reachability, [Consensus and Node](/en/human/architecture/consensus-and-node)
explains ordered delivery, [Implementation Status](/en/human/reference/implementation-status)
tracks built surfaces, and [agent Validator Operations](/en/agent/network/validator-operations)
is the edit-oriented twin.

## Propagation Seam

`crates/kernel/node` defines a byte-oriented transport seam and an in-process
loopback implementation. The loopback path exists for deterministic local
convergence tests: outbound messages are applied locally, encoded, and delivered
to peers; inbound messages are applied but not re-broadcast.

This path is useful for testing the node/host boundary, but it is not the live
consensus path for order-dependent roots.

## Ordered Consensus Path

`OrderedNode` applies finalized operations from an `Orderer`. The commonware
Simplex-backed orderer lives in `crates/kernel/consensus`, and `bin/node` wires
it into a real-socket validator process.

The ordered path is load-bearing because QMDB roots depend on operation order.
Validators must apply a shared finalized sequence, not whichever order their
transport happened to deliver.

## Valset State

`crates/system/valset` stores validator membership as a module. It exposes typed
messages and queries through valset's crate-root wire types, and the demo applies a join
message carrying an ed25519 public key.

Live orchestration around consensus epochs is implemented. `bin/node` feeds
finalized validator and resident membership into `ValsetOrchestrator`, schedules
the cutover, retargets mesh, state-sync, and reachability, then respawns the
ordered node over the new epoch's validator set. Remaining gaps are narrower:
demoted validators currently halt instead of degrading to resident/sync service,
and pre-recovery storage directories fail loudly rather than migrating.

## Identity Above Membership

Membership and quorum stay keyed by node identity: `valset`'s validator and
observer sets, and the epoch machinery above, never resolve a node key to a
person. `crates/system/identity` sits one layer above as a separate replicated
module: it maps node keys to user keys, so one person can run several nodes —
each with its own membership standing, its own vote, its own quorum weight —
while the app and every other consumer render them as one user. Binding a node
to a user is its own origin-and-user-signature-gated operation; it never
touches `valset`'s state or the cutover path described above.
