## Kernel

- `crates/kernel/sdk`: module contract, deterministic system API, and the
  shared snapshot codec (`sdk::codec`).
- `crates/kernel/host`: registry, dispatch, follow-up drain, commit/abort,
  global root-hash composition, and the worker seam (`host::worker`).
- `crates/kernel/node`: loopback and ordered node seams.
- `crates/kernel/consensus`: Simplex orderer, content store, relay, inbox,
  resolver fetch, scheme boundaries.
- `crates/kernel/statesync`: state-sync wire protocol and p2p binding.
- `crates/kernel/recovery`: op journal, checkpoints, boot-time replay.
- `crates/kernel/indexer`: derived node-local read index; never in the root-hash.
- `crates/system/capability-host`: machine-local executor providers.

## System

- `crates/system/kv`: QMDB byte-key module.
- `crates/system/valset`: validator membership state.
- `crates/system/saga`: deterministic continuation state.
- `crates/system/governance`: validator-set governance over valset.
- `crates/system/identity`: canonical accounts, member keys, display names, and
  node bindings.
- `crates/duckdns`: `<handle>.duck` → AccountId naming. A LIBRARY, not a
  module — the `gateway` module embeds it and owns the on-chain half.
- `crates/system/wireguard`: WireGuard tunnel-upgrade protocol;
  `wireguard::effect` is the apply layer.
- `crates/system/nat-traversal`, `reachability`, `data-plane`, `overlay-net`:
  hole punch, WireGuard mesh orchestrator, off-consensus byte transport,
  overlay seam.
- `crates/system/lifecycle`, `capability`, `dispatch`, and `tagging`: the
  module code registry, capability registry, capability-routed dispatch, and
  engagement routing.
- `crates/kernel/blobstore`: node-local content-addressed blob store, never in
  any root. `crates/modules/system/gateway`: `.duck` gateway route state.
- `crates/duckfs/client`: OS-side duckfs checkout/commit engine — chunk hashing,
  the versioned `.duckfs` index, worktree scan/status, change planning, and the
  sync `NodeApi` transport (HTTP). Never on the consensus path.
- wire surfaces: each module's typed payload and query shapes live at its crate root (`src/interface.rs`).

## Apps

- `crates/apps/pages`: QMDB page tree, blocks, and comments.
- `crates/apps/forge`: git-backed project state.
- `crates/apps/chat`: storage-owning chat module with hook fan-out.
- `crates/apps/agent`: agent registry, watches, run records.
- `crates/apps/tasks`: small canonical task state.
- `crates/apps/vaults`: replicated opaque secret ciphertext.
- `crates/apps/runs`: agent run composition, dispatch, response, and watch state.
- `crates/apps/inbox`: per-member notification queues.
- `crates/apps/automations`: operator rules over the chat hook seam.
- `crates/apps/files`: the duckfs module adapter; it owns the consensus
  filesystem surface and absorbed the old memory/workspace role as ordinary
  duckfs snapshots, paths, and `duck://files/...` evidence.
- `crates/apps/jobs`: consensus-native work board.

## Examples and Binaries

- `crates/examples/directory`: state-based directory module, registered in
  `bin/node` as the production canary.
- `crates/examples/greeter`: demo module emitting follow-up writes.
- `crates/examples/evm`: experimental QMDB-backed EVM module, in the
  `noded`/`simnode` genesis.
- `bin/node`: the p2p validator/mesh node and unified `ducktape` CLI. Its `fs`
  family owns the read and checkout/status/commit/pin loop over
  `crates/duckfs/client`; its `mcp` family runs the stdio tool server. There is
  no kernel-mount verb.
- `crates/noded`: the daemon library behind the http/ws app surface — the `/v1` router, actor lane, index/blob/stream lanes and the in-process testkit, served by `bin/noded` (the `ducktape-noded` process), `bin/node` and `bin/simnode`.
- `bin/simnode`: deterministic scenario node — noded's `/v1` wire over a
  test-scripted block producer.
- `bin/coordinator`: public or private rendezvous/STUN helper.
