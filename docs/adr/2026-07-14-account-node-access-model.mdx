# ADR: Account ↔ Node Access Model

Date: 2026-07-14. Status: **Accepted**, amended 2026-08-13: the submit door
no longer checks standing — any validly signed frame is admitted, and
per-module authorization moved on-chain into the `acl` module's dispatch gate
(allow-all by default). The client-standing plane (client invites,
`GrantClient`, the `clients` set) is deleted; "client standing" below is
historical. This document is the normative account/node/permission model the
desktop app, the node's RPC surfaces, and the thin-client work all build on.

## Context

"Thin client" started as a bespoke feature (a non-dev running a client-mode
node that tunnels to a dev's node). Working through it surfaced a simpler,
more general model: there is no separate "thin client" concept — there is an
**account** acting on a **node** through the node's RPC, and everything an
account does is signed by one of its keys. A non-dev "thin client" is just an
account with *client standing* consuming a node's *public* RPC. This ADR
states that model so the app and node stop conflating "workspace", "node",
and "user".

## Decision, in one table

| # | Rule | Where |
|---|------|-------|
| A1 | Every account↔node interaction is signed by an account key. No unsigned/impersonated writes. | §1 |
| A2 | A node exposes **two** RPC surfaces: **public** (data — query/submit, any account with a valid signature) and **private** (control — manage the node, owner only). | §2 |
| A3 | A client uses the public RPC; it needs no consensus/join status of the node — only "reachable or not". | §2, §3 |
| A4 | The node decides **how** it exposes its RPC: WireGuard-tunnel-via-coordinator, or self-expose (LAN/port-forward/public). The app just dials the resulting endpoint. | §4 |
| A5 | Node **control** requires: authenticated as the owner account (a bound key) **and** reachability of the node's **private** RPC. Only then does the node-control surface appear. | §2, §5 |
| A6 | The app is **account-first**: it presents the user (account) and its data; the node/workspace is plumbing, not a top-level tab. Node control is a *conditional* surface, not a peer of "user". | §5 |

## 1. Everything is account-key-signed (A1)

An account holds one or more ed25519 keys (identity + bound device/user keys).
Every op an account submits is a frame signed by one of those keys, so
consensus attributes it to the account, not to the node relaying it.

- **Public data ops** (chat, pages, files, forge, tasks, …): the app signs
  the frame with the account's key and submits over `/v1/submit/frame`; the
  serving node is a courier that never re-signs (shipped: PR #579, the
  `user_sign_frame` command + `signPayload` transport lane). The submit door
  admits **any validly signed frame** — the signature is the whole door
  (2026-08-13 amendment; `verify_relay_submit` checks no standing set).
  Per-module authorization is decided at dispatch: the `acl` module's
  on-chain policy table (allow-all by default, governance-tightened) plus
  each module's own semantic origin gates.
- **Control ops** (admit, promote, shutdown, config): signed by the **owner**
  account's bound key, accepted only on the private RPC (§2).

Consequence: "who did this" is always an account key in consensus, never the
node's shared key. The pre-existing frameless `/v1/submit` (node-key-stamped)
is the local-daemon convenience lane only; it is not the account model.

## 2. Two RPC surfaces: public (data) vs private (control) (A2, A5)

A node serves two distinct RPC surfaces:

- **Public RPC** — reads and account-signed writes (`/v1/query`,
  `/v1/submit/frame`, `/v1/index/*`, `/v1/files|fs/*`, browse). Any account
  may use it; authorization is the per-op signature + the acl module's
  dispatch policy + the module's own origin gates. A consuming account needs
  no prior grant of any kind.
- **Private RPC** — node management (admit joiners, promote/demote, schedule
  upgrades, shutdown, edit config). Owner-only: accepted only from the owner
  account's bound key, and only reachable when the node chooses to expose the
  private surface. This is where "node control" lives.

The split is the load-bearing idea: a client can never reach control ops even
if it can reach the node, because control is a *separate surface* gated on
owner identity, not just a permission check on one endpoint.

## 3. A client needs no node status (A3)

A consuming account does not run the join gate, statesync, or the
consensus-phase machinery — those are for members obtaining chain state
(statesync stays fail-closed on valset, PR #567; nothing about submitting
grants sync). A client only needs to know the public RPC is **reachable**; it
reads/writes through it. The app's remote-connection path should therefore
skip the member-status/standing dance for a pure client connection and treat
it as "connected or not".

## 4. The node owns its exposure (A4)

How the public (and, for the owner, private) RPC becomes reachable is the
**node's** decision, per deployment — not a global architecture choice:

- **WireGuard tunnel via coordinator**: the node registers with the
  coordinator; a connecting account brings up a WireGuard tunnel to it
  (coordinator brokers rendezvous/hole-punch, reusing the invite first-contact
  machinery), and the RPC is served over the tunnel. Works through NAT;
  requires a small tunnel bring-up on the connecting side.
- **Self-expose**: the node is directly reachable (LAN, port-forward, public
  host / VPS), and the app dials the URL. Zero connecting-side machinery — this
  is the existing "Remote" transport.

The app treats both identically: it is handed an endpoint (a URL, or a
tunnel-local address) and speaks `/v1` to it. The relay-vs-tunnel question
dissolves into "which exposure did the node's operator choose."

## 5. Account-first UI (A5, A6)

The app is organized around the **account**, not the node/workspace:

- The primary lens is the user (account) and its data; the network explorer is
  an account-scoped view. The historical user↔node / workspace tab split is
  plumbing the user should not have to think about.
- **Node control is a conditional surface**, shown only when the signed-in
  account is the node's **owner** *and* the node's **private** RPC is
  reachable (A5). A non-owner, or an owner without private-RPC reach, simply
  does not see node-management controls — it is not a disabled tab, it is
  absent.
- A remote connection to someone else's node presents *only* the account
  using that node's public RPC — no node-management chrome at all.

## Non-goals / accepted limits (v1)

- No coordinator HTTP relay: exposure is WireGuard (p2p, e2e) or direct. The
  coordinator stays rendezvous-only (its documented invariant).
- A hard-NAT pair that cannot hole-punch and where the node has not
  self-exposed cannot connect. Acceptable — the node operator can self-expose.
- The account-first UI restructure is a large navigation change; it gets its
  own design pass before implementation.
