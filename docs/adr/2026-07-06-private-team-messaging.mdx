# ADR: Secure Private Team Messaging — direction fixed, build deferred

Date: 2026-07-06 · Status: **Accepted as direction, deferred as work** — too
heavy for the current product phase; recorded so the thinking is not
re-litigated when messaging privacy becomes current.

## Context

The requirement, precisely: **private means private from the other network
members.** A conversation's content must be readable by its participants and
by no one else — including every other member node in the same private
network, each of which replicates the full consensus state. The network
perimeter (WireGuard data plane, E2E-encrypted authenticated mesh,
rendezvous-only coordinator, no third-party services)
is necessary but is NOT the read barrier; the read barrier must be
cryptographic, because state replication hands every member node every byte.

What already holds and any future build leans on:

- **Authorship integrity.** Every submit on the real node lane is an
  ed25519-signed op frame under the workspace key; a claimed origin cannot
  ride a signed frame (`bin/node/src/main.rs:6929-6945`). Chat derives
  `AuthorRef` from the verified origin (`crates/apps/chat/src/lib.rs:155-164`).
  One workspace = one node = one member identity.
- **Membership = network membership.** valset
  (`crates/system/valset/src/lib.rs`) is the consensus roster; the WireGuard
  peer set derives from it; profiles maps keys to display names.
- **Ordering, durability, late-join.** Consensus total order, per-channel
  gap-free sequences, revisions, statesync of full history.
- **Trust-model precedent.** vaults
  (`crates/apps/vaults/src/interface.rs:1-14`): ciphertext-on-consensus,
  client-side encryption to recipients, on-chain ACL = write-integrity and
  recipient bookkeeping, crypto = the only read barrier.

The gap, confirmed in code (still true as of this ADR): chat bodies are
plaintext in qmdb and `ChatQuery` serves any channel to any caller;
`PostPolicy::MembersOnly` gates writes only; `SetMembership`/`RegisterHook`
accept **any** origin (`crates/apps/chat/src/interface.rs:217-233`); no
owners, no private channels, no DMs. The legacy `noded` lane stamps an
unauthenticated origin — privacy claims only ever hold on the signed-frame
`bin/node` lane.

## Options considered

- **A. Governance hardening only (no crypto).** Owners, gated
  membership/hooks, a `Private` visibility hiding channels from non-member
  queries. Fails the requirement outright — any member node reads the
  plaintext replica; curtains, not locks. Never an acceptable definition of
  "private" on its own.
- **B. A + encrypted lanes (vaults pattern) — the chosen direction.**
  Private channels and DMs store opaque ciphertext in consensus state;
  content sealed to a per-channel **epoch key** wrapped per participant with
  X25519 envelopes. Consensus keeps ordering/durability/late-join/authorship;
  crypto supplies the one thing consensus cannot: confidentiality against
  replicas.
- **C. Off-consensus messaging over `crates/system/data-plane`.** Right
  shape for insider-metadata privacy and ephemera (consensus-derived
  default-deny `AdmissionPolicy`, WireGuard-bound peer identity) but has no
  real transport arm yet (sim only) and forfeits ordered durable history,
  offline delivery, and new-member sync. Deferred substrate, not the carrier
  for message history.

## Decision

1. **Direction fixed:** when private messaging is built, it is approach B on
   the existing chat module — not a new plane, not MLS, not off-consensus.
   Sketch of record: per-channel epoch keys (epoch 0 at create; rotate
   **atomically in the remove op** so there is no leak window; new members
   get all epochs wrapped — Slack history semantics); message bodies gain a
   `sealed {epoch, nonce, ct}` arm (XChaCha20-Poly1305, AAD =
   `(channel_id, message_id, epoch, author_key)`), stored opaquely, no
   crypto in `execute`; members publish a messaging X25519 pubkey via an
   origin-gated profiles write (consensus authorship is the ed25519↔X25519
   binding, same trick as WireGuard tunnel keys); crypto runs in the
   member's **node** behind `/v1/crypto/{pubkey,seal,open}` routes (keys
   never in the webview; also finally serves vaults); DMs are two-member
   private channels with deterministic id `dm:<min>:<max>`, created
   atomically with the first message; channels default **private**, public
   plaintext is the explicit opt-out (and is where hooks/agents/search keep
   working — sealed bodies can't feed them).
2. **Build deferred:** the full build (new msg arms + state fields is
   consensus-breaking → lockstep or height-gated upgrade; node crypto
   routes; app surface) is overkill for the current phase. No
   implementation plan is scheduled.
3. **Independently worthwhile hygiene, not scheduled but fair game** the
   next time chat is touched: owner-gating the currently any-origin
   `SetMembership`/`RegisterHook` (today anyone can join any channel or
   attach hooks to it). This is a correctness hole regardless of the privacy
   feature — closing it must not be sold as "private messaging".

## Consequences

- Until built, **nothing in the product may be labeled private messaging**:
  every channel is readable by every member node.
- Accepted residual even when built (v1): **content sealed, participation
  visible** — membership, timing, sizes, reaction emoji, and DM pairing (the
  deterministic id) replicate to all member nodes. Hiding participation
  on-consensus is not honestly achievable (deterministic write-gating needs
  plaintext member sets; a small enumerable roster makes hashed membership
  brute-forceable). If who-talks-to-whom must ever be hidden, that
  conversation leaves replicated state — approach C is the seam.
- No per-message forward secrecy (epoch keys, not a ratchet — the epoch seam
  is where a ratchet would slot in); no deniability (signed frames are the
  point); no multi-device (one workspace = one node = one key); key loss =
  social recovery (owner re-wraps to the member's new key).
- Caps that shaped the record design: envelopes ~100 B/member under the
  256 KiB record bound → ≤1024 members and ≤256 epochs per private channel;
  sealed `ct` rides the existing 64 KiB head bound.
