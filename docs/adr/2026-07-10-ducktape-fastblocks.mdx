# ADR: Ducktape Fastblocks — 100 ms Quorum-Certified Preconfirmations

Date: 2026-07-10. Status: **Proposed**.

This ADR defines sub-second transaction feedback for Ducktape. Validators may
publish up to ten quorum-certified, append-only increments during the existing
one-second batch window. A client may call a transaction **preconfirmed** only
after receiving a transferable quorum certificate. Simplex remains the only
source of canonical order, execution, height, app hash, and finality.

This revision adopts a strict **reuse-first** constraint: Fastblocks extends
the component that already owns an invariant instead of building a parallel
stack. In particular, it does not introduce another leader election, mempool,
canonical payload, consensus engine, content store, recovery database, epoch
watcher, RPC server, or UI operation ledger.

Merging this ADR ratifies a protocol direction. It does not claim that the
100 ms target has been achieved. Binding activation is separately gated by a
coordinated validator upgrade, adversarial tests, and measurements on the
intended validator topology.

## Decision

Ducktape will add a validator-only protocol named **PromiseNet** over one
dedicated per-use `DataPlane` instance. During an eligible canonical build
window, the validator that Simplex already elected for the active view acts as
the temporary **assembler**. It reserves an append-only prefix from the
existing `OrderedNode` custody queue and asks the epoch validator set to
certify each increment.

For `n` validators, Fastblocks uses the same Commonware `N3f1` quorum rule as
Simplex:

```text
f = floor((n - 1) / 3)
q = n - f
```

A proposal, transport-authenticated packet, assembler signature, or
availability certificate is not a preconfirmation. The externally meaningful
evidence is a **Promise Quorum Certificate** (`PromiseQC`) assembled from at
least `q` post-lock acknowledgements. Before an honest validator contributes
such an acknowledgement, it must:

1. validate and durably retain the exact transaction frames;
2. verify a `q`-validator availability certificate for the proposal;
3. durably install a promise lock; and
4. make the existing Simplex proposal verifier reject any canonical successor
   that omits or reorders the locked prefix.

The v1 guarantee is **ordered inclusion**, not successful execution. A valid
receipt says that its frame must occur in the first finalized canonical
successor of the named parent boundary. Normal deterministic execution may
still reject the operation. No pending state, speculative receipt, or external
side effect becomes final before Simplex finality.

The protocol uses these fixed or derived parameters:

| Parameter | v1 value | Existing owner or derivation |
|---|---:|---|
| canonical build window | 1 s | `consensus::BLOCK_TIME` |
| fastblock period | 100 ms | the existing node drain cadence, promoted to shared `BlockCadence` configuration |
| maximum increments | 10 | `BLOCK_TIME / FASTBLOCK_PERIOD` |
| tolerated faults | `f = floor((n - 1) / 3)` | Commonware `N3f1` |
| certificate quorum | `q = n - f` | Commonware `N3f1` |
| canonical payload | existing `encode_batch` bytes | `crates/kernel/node` |
| maximum promised capacity | one existing canonical batch | the shared batch builder and `MAX_BATCH_BYTES` |
| certificate scheme | epoch's active `ConsensusScheme` | existing Ed25519/BLS selection and epoch key material |
| data-plane service | `Service::Promise = 5` | append-only service registry |
| stream / datagram ports | `45805` / `45905` | existing per-use port derivation convention |
| fallback | ordinary Simplex | existing flush and proposal path |

The 100 ms period is a scheduling and service-level target, never a safety
input. A late certificate produces a missed increment, not a smaller quorum,
weaker receipt, or altered signed subject.

## Reuse and Integrity Rule

Every implementation choice follows this order:

1. **Reuse unchanged** when an existing component already owns the required
   invariant.
2. **Extend that owner** when Fastblocks adds state to the same invariant.
3. **Add a new mechanism** only where no existing component can safely own the
   obligation.

“Reuse” does not mean sharing unsafe mutable state, overloading an unrelated
wire service, or hiding promise records in an unversioned blob. Isolation that
protects an existing invariant—such as a separate per-use data-plane
instance—is intentional integrity, not duplication.

| Responsibility | Existing owner | Decision | Fastblocks delta |
|---|---|---|---|
| leader and view lifecycle | Simplex `ConsensusAutomaton` / `SimplexReporter` | extend | publish authoritative open/close events; no second election |
| cadence | `BLOCK_TIME`, `DRAIN_TICK`, node flush loop | extend | one `BlockCadence`; fast cuts use the existing beat |
| validator membership | epoch respawn / valset orchestrator | reuse | PromiseNet receives the same finalized validator snapshot |
| keys and quorum certificates | `ConsensusScheme`, Commonware certificate `Scheme`, `N3f1` | extend | a Fastblock subject adapter and separate signature namespace |
| frame identity and validation | `FrameId`, `frame_id`, `decode_frame` | reuse | none |
| custody and FIFO order | `OrderedNode::outstanding` and `pending_batch` | extend | reservation, deduplication, and leader forwarding; no second mempool |
| capacity and encoding | `encode_batch`, `decode_batch`, `MAX_BATCH_BYTES`, current packer | refactor then reuse | extract one `BatchBuilder` used by ordinary and fast paths |
| canonical proposal and execution | `Orderer`, `ContentStore`, Simplex, `OrderedNode::drain_delivered` | reuse unchanged | locked-prefix check before a Simplex vote |
| payload availability | consensus `ContentStore`, eager relay, resolver | reuse | Promise body streams populate the same content-addressed store |
| durable safety state | `BlockSink`, `Recovery`, `recovery-oplog`, `Manifest` | extend | namespaced promise records and unresolved-lock checkpoint state |
| network transport | `DataPlane`, `OverlaySockets`, flow policies and stats | instantiate existing abstraction | one isolated `Service::Promise` plane |
| API actor and stream | `NodeCommand`, `/v1/submit`, `StreamHub` | extend | FrameId progress and receipt events on existing surfaces |
| desktop operation state | `OpLedger` and optimistic projection | extend | one evidence-gated `preconfirmed` phase |
| activation and cutover | height-gated upgrade, `R = n`, epoch respawn | reuse | Fastblocks is another coordinated protocol-version capability |

The only genuinely new safety mechanism is a small, shared
**`PromiseGuard`**. It serializes the one cross-protocol race: an honest
validator must never both acknowledge a new promise and authorize an omitting
canonical proposal for the same parent. The two-phase PromiseNet state
machine, its signed subjects, and portable client receipt are also new because
no existing Ducktape component represents a preconfirmation obligation.

This decision specifically removes the earlier draft's proposed
`CanonicalBatchV2`, certificate sidecar, standalone Fastblocks storage, fixed
Ed25519-only certificate format, and new kernel crate. The ordinary encoded
batch remains the canonical payload.

## Context

Ducktape already feels fast locally but does not yet make a network promise.
The app immediately applies a reversible optimistic projection. Its operation
ledger then waits in `pending` until `/v1/submit` returns the finalized block
or fails. The node gives a signed frame a stable content address, `FrameId`,
and keeps accepted frames in `OrderedNode` custody. A submit timeout is
ambiguous because the frame may still finalize later.

The current canonical path already provides most of the machinery needed:

- `consensus::BLOCK_TIME` is one second.
- The node pump wakes on a 100 ms `DRAIN_TICK` and flushes its FIFO once per
  block window.
- `OrderedNode` owns accepted-frame custody, cutover carry, FIFO batching,
  exact frame decoding, and the canonical `encode_batch` format.
- `ConsensusAutomaton::propose(Context)` is called in the elected Simplex
  proposer context and waits for the canonical pending FIFO.
- `ConsensusAutomaton::verify` already gates a vote on local payload
  availability in `ContentStore`.
- `SimplexReporter` observes consensus activity and owns the finalization
  transition.
- `ContentStore` and the existing payload resolver provide a content-addressed
  availability path for canonical bytes.
- `Recovery` provides journal-before-action hooks, checkpoint manifests,
  replay, and epoch cutover records.
- `ConsensusScheme` already selects Ed25519 certificate collections or BLS
  aggregate certificates per epoch.
- The height-gated upgrade path already requires `R = n` validator readiness
  and tears down and respawns epoch-scoped engines.
- `NodeCommand`, `StreamHub`, and the app's `OpLedger` already own submission
  and user-visible finalization progress.

Base Flashblocks is product inspiration, not a trust model to copy. Base's
active sequencer emits cumulative partial block updates approximately every
200 ms during a two-second L2 block. Ducktape has no single sequencer whose
statement should become a BFT guarantee. Its receipt must remain enforceable
after an assembler crash or Simplex view change, so a validator quorum—not the
temporary assembler—must own the promise.

## Goals

- Target one new certified increment every 100 ms when quorum network and
  storage latency permit.
- Return independently verifiable evidence for a specific existing `FrameId`.
- Preserve a receipt across assembler failure, view change, process restart,
  ordinary packet loss, and certificate withholding.
- Keep exactly one canonical consensus, payload format, execution path, and
  app-state commit path.
- Reuse existing custody, packing, availability, recovery, membership,
  upgrade, API, and UX owners.
- Bound promised work to what the next ordinary canonical batch can contain.
- Degrade to the current Simplex path when no binding promise exists.
- Tell the truth about optimism, custody, preconfirmation, rejection, and
  finality.
- Leave speculative execution to a separate protocol decision.

## Non-goals

- Reducing canonical Simplex finality to 100 ms.
- Guaranteeing that every accepted transaction gets a preconfirmation.
- Increasing canonical throughput; Fastblocks divide existing capacity.
- Guaranteeing successful module execution, fees, effects, or a wall-clock
  finalization deadline.
- Treating a local optimistic projection, one validator, one assembler, an
  RPC response, or WireGuard identity as quorum evidence.
- Replacing Simplex with another chain, DAG, or 100 ms consensus engine.
- Creating a second mempool, canonical batch codec, recovery database,
  validator-set watcher, or client transport.
- Exposing Base-like pending state in v1.
- Allowing a binding promise to cross a validator-set or protocol-version
  cutover.

## Terminology and Guarantee

**Parent boundary** is the finalized tuple
`(network_id, epoch, app_height, app_hash)` from which the next canonical
application block executes.

**Assembler** is the validator Simplex elected to propose the active view. It
chooses candidate order and performs fan-out; it has no unilateral authority.

**Candidate increment** is an append-only delta proposed at one fastblock
index. It becomes a **fastblock** only when accompanied by a valid `PromiseQC`.

**Certified prefix** is the ordered concatenation of all contiguous certified
increments starting at index zero.

**Promise lock** is a validator's durable obligation to reject a canonical
successor that does not begin with its locked prefix.

**Canonical successor** is the first finalized application block after the
receipt's parent boundary. Nullified views and cutover-discarded deliveries do
not count.

For a structurally valid frame `F`, a valid receipt means:

> Assuming at most `f` Byzantine validators in the named epoch, any canonical
> successor of the named parent boundary that finalizes must contain `F` at the
> certified position. Its deterministic execution may still reject it.

This is a safety promise, not a liveness promise. If promised data cannot be
recovered, canonical progress may stop rather than violate a receipt. If no
binding lock exists, PromiseNet failure does not block ordinary Simplex.

## Fault and Network Model

The protocol assumes:

- the same epoch participant set, ordering, public keys, active
  `ConsensusScheme`, and `N3f1` quorum configuration as Simplex;
- at most `f` Byzantine validators in the epoch;
- unforgeable signatures and collision-resistant hashes;
- crash-recoverable storage for prepared votes, bodies, and locks;
- deterministic existing frame decoding and batch encoding; and
- eventual synchrony for liveness, with no clock or delay bound required for
  safety.

Messages may be delayed, duplicated, dropped, reordered, replayed, or
withheld. An assembler may equivocate or disappear at any write boundary. A
validator may restart from its last durable record. Local clocks may decide
when to attempt work but never whether a certificate, lock, or receipt is
valid.

PromiseNet admits exactly the finalized **validator** set for the epoch.
Residents retain their existing submission and follower roles and never vote
on Fastblocks.

## Reuse-First Architecture

```text
existing client / resident submission
                 |
                 v
       NodeCommand + relay lane
                 |
                 v
       OrderedNode custody FIFO  <---- forwarded FrameId/body from validators
                 |
      shared BatchBuilder preview/reservation
                 |
                 v
     elected Simplex proposer = PromiseNet assembler
                 |
      +----------+-----------+
      |                      |
 Promise control       Promise body flows
      |                      |
      +----------+-----------+
                 v
          epoch validators
        prepare -> AvailabilityQC
        lock    -> PromiseQC
                 |
                 v
       verified receipt event

certified reservation + optional ordinary tail
                 |
                 v
       existing encode_batch bytes
                 |
                 v
 ContentStore -> Simplex -> OrderedNode drain -> existing execution/finality
```

PromiseNet is an adjunct to the existing orderer, not a second ordering
system. All safety-bearing transitions re-enter the node actor that owns
custody, recovery, and the `PromiseGuard`. Network receive, body hashing, and
signature verification may happen off-loop, but the actor serializes queue
reservation, durable prepare, durable lock, canonical authorization, release,
and cutover.

There is one assembler because one component must select an order and cut a
window. BFT does not eliminate this coordination role; it prevents that role
from being authoritative by itself.

## Leader and Window Lifecycle

PromiseNet does not calculate or elect a leader. The existing
`ConsensusAutomaton::propose(Context)` callback is the authoritative open
signal: Commonware invokes it for the validator selected for that Simplex
view. The automaton publishes the view and parent to the node coordinator,
then continues its existing wait for a digest on the same canonical pending
FIFO.

`SimplexReporter` is extended to publish authoritative view closure,
nullification, and finalization events from the activity stream it already
observes. PromiseNet must not infer leadership from wall time, a peer claim,
or a locally predicted round-robin index.

A window is eligible only when all of the following are true:

- the parent boundary is finalized and locally recovered;
- the current validator is the Simplex proposer for the callback's view;
- the consensus pending FIFO has no older canonical payload ahead of this
  window;
- no binding promise or canonical authorization exists for the parent;
- no armed membership or binary cutover can consume the successor;
- a durable `PromiseSafetySink` is available; and
- the PromiseNet health circuit is closed.

The session identifier is:

```text
session_id = H(
  "ducktape/fastblocks/session/v1",
  network_id,
  epoch,
  parent_height,
  parent_app_hash,
  assembler_view,
  assembler_identity
)
```

Exactly one PromiseNet session may issue acknowledgements for a parent in v1.
It closes on the earliest of:

- ten certified increments;
- the shared one-second build deadline;
- canonical authorization by this validator;
- assembler view loss or nullification;
- parent successor finalization;
- epoch freeze; or
- the fast-path circuit breaker.

After view loss, the next Simplex proposer recovers and seals any existing
lock but does not start a second promise session on that parent. This trades
some fast-path liveness for a small, auditable lock space. A future safe-session
transfer protocol requires its own ADR.

The healthy schedule is:

| Offset | Existing/new action |
|---:|---|
| `0 ms` | Simplex proposer callback opens the window; shared builder previews increment 0 |
| `0–100 ms` | body validation, durable prepare, `AvailabilityQC`, durable lock, `PromiseQC` |
| `100 ms` | publish receipt for index 0 and preview the next delta |
| `200–900 ms` | repeat while the cumulative ordinary batch still fits |
| `1000 ms` | atomically close the guard, encode one ordinary batch, pin, and submit to the existing orderer |

`BLOCK_TIME`, the 100 ms node beat, and the automaton's proposal wait become
fields of one `BlockCadence` value so the host and automaton cannot drift onto
independent timers. Queue notification may replace polling, but it does not
create another clock. A small seal grace may extend the automaton's idle wait;
the canonical target remains one second.

A transaction arriving immediately after a cut can wait almost one period for
the next candidate and another period for two quorum phases. The honest user
expectation is therefore approximately 100–200 ms in the target topology, not
a universal 100 ms upper bound.

## PromiseNet Data Plane

PromiseNet instantiates the existing `DataPlane<OverlaySockets>` abstraction
with its own queues, flow policy, stats, and overlay ports:

- append `Service::Promise = 5` to the wire-stable service registry;
- reserve stream port `45805` and datagram port `45905` on each validator's
  overlay `/128`;
- use an epoch-scoped, validator-only `AddressBook` and default-deny
  `AdmissionPolicy`; and
- bring it up through the existing overlay wiring and refresh its admission set
  at the same epoch cutover that respawns consensus.

Suffix `4` remains a tombstone for the removed DuckDNS Web plane. Reusing it
would violate the append-only service registry seen by older binaries.

The current statesync `OverlayBook` pattern is generalized into a reusable
service-parameterized epoch peer book. Statesync continues to admit its
transport set; PromiseNet supplies the consensus-validator subset and
`Service::Promise`. This removes duplicated ULA derivation, reverse lookup,
and cutover refresh logic without sharing service queues or admission scopes.

| Flow | Existing transport class | Contents | Integrity rule |
|---|---|---|---|
| control | persistent stream | proposals, attestations, certificates, recovery summaries, NACKs | authoritative and backpressured |
| body | stream | frame bodies and digest-directed fetches | independently bounded; never blocks control |
| vote hint | datagram | duplicate attestation hint | optional; authoritative stream retry remains |
| head hint | datagram | latest session/index/subject | optional and discardable |

WireGuard peer identity performs early admission and attribution. Portable
protocol evidence still carries a validator attestation or certificate.
Datagrams are never the only copy of safety-bearing information. Queue
overflow drops hints and disables the fast path; it does not allocate without
bound or weaken validation.

PromiseNet does not introduce a second content-addressed store. Received
frame bytes are keyed by the existing `FrameId = H(encoded_frame)` and placed
in the epoch's existing consensus `ContentStore`. A durable promise prepare
causes those same bytes to be restored into `Recovered.frames`, which the boot
path already pins into `ContentStore`. The existing canonical eager relay and
resolver remain the correctness backstop for the final `encode_batch` payload.

## Intake, Selection, and Shared Batching

Ingress retains the current contract:

1. validate size, signature, and `decode_frame`;
2. calculate the existing stable `FrameId`;
3. enter `OrderedNode::outstanding` custody and `pending_batch` FIFO; and
4. carry unresolved custody across an epoch cutover under the same FrameId.

When Fastblocks is active, a validator forwards newly accepted byte-identical
frames to the authoritative assembler. The assembler admits them through the
same `submit_frame` function. `submit_frame` is extended to make duplicate
`FrameId` insertion idempotent; forwarded data does not enter a PromiseNet-only
mempool.

Before protocol work, the existing greedy logic in `flush_batch` is extracted
as one `BatchBuilder`/`BatchPlan` abstraction. It owns:

- FIFO member order;
- exact `varint(count) || varint(len) || bytes` size accounting;
- `MAX_BATCH_BYTES` and the current single-member edge case;
- previewing a prefix without removing custody;
- reserving and later draining the exact previewed FrameIds; and
- encoding through the existing `encode_batch` function.

Both the disabled path and Fastblocks call this helper. A golden regression
test must prove that ordinary `flush_batch` produces byte-identical batches
before and after extraction.

Fastblocks subdivide one existing batch budget. At index `i`, the assembler
asks `BatchBuilder` for the longest additional FIFO prefix whose cumulative
ordinary encoded length is within the proportional target:

```text
target(i) = floor(existing_one_batch_target * (i + 1) / 10)
```

The builder—not PromiseNet—decides whether a frame fits, including the existing
single-member rule. There is no separately maintained promise byte formula and
no wrapper overhead to reserve. A large frame waits for a later index or the
ordinary path. Overload yields fewer preconfirmations, not extra canonical
capacity.

Each candidate carries only new frame bodies but commits to the cumulative
ordered FrameId root, count, and ordinary encoded length. An existing
certified reservation can only grow. At seal:

1. the certified prefix is taken first, byte-identical and in order;
2. unpromised frames from the same FIFO may fill the remaining capacity;
3. overflow stays in custody for a later canonical batch; and
4. the resulting ordinary `encode_batch(members)` bytes follow the existing
   `sink.pin -> orderer.submit` path.

If no promise lock exists, the reservation can be released and the existing
ordinary `flush_batch` behavior is the fallback. If a lock exists, the prefix
cannot be released by a timeout or circuit breaker.

## Cryptography and Wire Protocol

Fastblocks reuse the epoch's certificate implementation rather than defining
an Ed25519-specific signature vector. A small `EpochCertificateSuite` factory
derives both the Simplex scheme and a Fastblock scheme from the same:

- ordered participant set;
- validator identity and signing key material;
- active `ConsensusScheme` (`V1Ed25519` or `V2Bls`); and
- Commonware certificate codec, attestation verification, assembly,
  certificate verification, and `N3f1` quorum implementation.

The Fastblock scheme uses a distinct namespace and a Fastblock-specific
subject type. A Simplex vote can never verify as a Promise vote even though the
key source and certificate primitive are shared. Under Ed25519, the existing
scheme encodes a collection of attestations. Under BLS, it uses the existing
aggregate signature and signer-index representation. PromiseNet must not
implement another bitmap, signer sort, aggregation format, or quorum counter.

The following are semantic schemas; exact Rust associated types depend on the
active scheme. Encoding follows the repository's existing bounded,
length-delimited wire helpers and Commonware certificate codec. Every top-level
object starts with a protocol version and rejects unknown versions.

```rust
struct ParentBoundaryV1 {
    network_id: [u8; 32],
    epoch: u64,
    app_height: u64,
    app_hash: [u8; 32],
}

struct ProposalCoreV1 {
    parent: ParentBoundaryV1,
    session_id: [u8; 32],
    assembler_view: u64,
    assembler: ValidatorId,
    index: u8,                         // 0..=9
    previous_promise_subject: Option<[u8; 32]>,
    delta_frame_ids: Vec<FrameId>,
    delta_frame_root: [u8; 32],
    cumulative_frame_count: u32,
    cumulative_encoded_bytes: u32,
    cumulative_frame_root: [u8; 32],
}

enum FastblockSubjectV1 {
    Proposal { proposal_hash: [u8; 32] },
    Availability { session_id: [u8; 32], index: u8, proposal_hash: [u8; 32] },
    Promise { session_id: [u8; 32], index: u8, proposal_hash: [u8; 32] },
    LockNack { session_id: [u8; 32], index: u8, proposal_hash: [u8; 32] },
}

struct SignedProposalV1 {
    codec_version: u16,               // 1
    core: ProposalCoreV1,
    assembler_attestation: SchemeAttestation,
}

struct AvailabilityQCV1 {
    codec_version: u16,
    subject: FastblockSubjectV1::Availability,
    certificate: SchemeCertificate,
}

struct PromiseQCV1 {
    codec_version: u16,
    subject: FastblockSubjectV1::Promise,
    certificate: SchemeCertificate,
}

struct LockNackV1 {
    codec_version: u16,
    proposal: SignedProposalV1,
    availability_qc: AvailabilityQCV1,
    validator_attestation: SchemeAttestation,
}

struct CertifiedIncrementV1 {
    proposal: SignedProposalV1,
    availability_qc: AvailabilityQCV1,
    promise_qc: PromiseQCV1,
}

struct FastblockReceiptV1 {
    codec_version: u16,
    parent: ParentBoundaryV1,
    frame_id: FrameId,
    frame_position: u32,
    certified_chain: Vec<CertifiedIncrementV1>,
    frame_membership_proof: FrameMerkleProofV1,
}
```

Every signed subject transitively binds network, epoch, parent, session,
assembler view, index, proposal hash, and role. Domain namespaces are distinct
for proposal, availability, promise, and NACK attestations.

Certificate serialization is proof material, not chain identity. Different
valid signer subsets may produce different certificate bytes for the same
semantic proposal. The next increment therefore links:

```text
proposal_hash = H("ducktape/fastblocks/proposal/v1", canonical(ProposalCoreV1))

promise_subject = H(
  "ducktape/fastblocks/promise-subject/v1",
  session_id,
  index,
  proposal_hash
)
```

`previous_promise_subject` contains this signer-set-independent value, never a
serialized certificate hash. A Promise acknowledgement signs the proposal
subject after verifying any valid AvailabilityQC for it. This prevents
multiple valid quorum encodings from creating artificial branches.

The receipt's only new generic cryptographic helper is a domain-separated
Merkle commitment over ordered `FrameId`s. It exists to keep a per-frame
receipt bounded without copying every ID. It has no database or canonical
state; roots and proofs are recomputed from the `BatchPlan`. A straightforward
full-ID proof mode may be retained for test vectors, but production decoders
enforce maximum chain, ID, proof, certificate, and total receipt sizes before
allocation.

## Validator State Machine

Each validator owns at most one unresolved boundary state:

```rust
struct PromiseStateV1 {
    parent: ParentBoundaryV1,
    phase: BoundaryPhaseV1,
    session: Option<SessionStateV1>,
    certified_prefix: Vec<FrameId>,
    prepared: Option<PreparedV1>,
    locked: Option<LockedV1>,
}

enum BoundaryPhaseV1 {
    Open,
    CanonicalClosed { first_payload_digest: [u8; 32] },
    Finalized { payload_digest: [u8; 32] },
    Frozen,
}

struct PreparedV1 {
    index: u8,
    proposal_hash: [u8; 32],
    delta_frame_ids: Vec<FrameId>,
}

struct LockedV1 {
    index: u8,
    proposal_hash: [u8; 32],
    cumulative_frame_ids: Vec<FrameId>,
    availability_qc: Vec<u8>,         // bounded scheme encoding
}
```

Before releasing an availability attestation, a validator must:

- validate epoch, parent, authoritative view, assembler, session, index, and
  exact previous promise-subject link;
- verify the assembler attestation and previous certified chain;
- possess every full delta frame and run the existing size, signature,
  `decode_frame`, and `FrameId` checks;
- reject duplicates and any rewrite of the prior prefix;
- recompute roots and exact encoded capacity through `BatchBuilder`;
- pass local disk and queue limits; and
- durably write one `PromisePrepared` record that binds the anti-equivocation
  key, proposal, and delta bodies before signing.

The availability attestation means “I validated and can serve these bytes.” It
is not a user-visible promise.

Before releasing a Promise acknowledgement, a validator must:

- verify a complete `AvailabilityQC` through the epoch certificate suite;
- possess and durably retain the complete cumulative prefix even when it did
  not sign the availability phase;
- verify that the proposal uniquely and contiguously extends its lock;
- acquire the shared `PromiseGuard` while the parent is still open;
- append and fsync `PromiseLocked`; and
- publish the new lock to the Simplex verifier before releasing its
  attestation.

The assembler uses the same Commonware assembly function to form a
`PromiseQC`, broadcasts it on the control flow, and emits per-frame receipts.
A validator treats its own Promise acknowledgement as binding immediately;
the assembler may hide a completed certificate from its signers or reveal it
only to a client.

The two phases are deliberate. Accepting the availability quorum directly
would let a Byzantine assembler collect signatures, reveal them only to a
client, and disappear before honest validators durably learned that they must
constrain canonical consensus. `PromiseQC` proves that a quorum attested only
after verifying availability and installing the constraint.

## Durability and Recovery Reuse

Fastblocks does not create a second WAL or database. `Recovery` implements a
new `PromiseSafetySink` facet using the existing `recovery-oplog`, record codec,
sync policy, manifest store, and boot replay. `OrderedNode` exposes binding
PromiseNet operations only when its sink implements this facet; `NullSink`
cannot issue binding acknowledgements.

The journal gains append-only record tags:

| Record | Contents | Durability point |
|---|---|---|
| `PromisePrepared` | parent/session/index, proposal hash, anti-equivocation key, exact new frame bytes | append + sync before availability attestation |
| `PromiseLocked` | proposal hash, cumulative ordered FrameIds, bounded AvailabilityQC bytes | append + sync before Promise acknowledgement |
| `PromiseReleased` | parent/session/proposal key, canonical digest and matching/omission reason | append + sync before deleting prepared or locked in-memory state |

`PromisePrepared` is also a durable content pin. Recovery exposes its frame
bodies through the existing `Recovered.frames` collection so boot uses the
existing `ContentStore::pin` path. There is no PromiseNet blob store.

An acknowledger that did not participate in availability first performs an
idempotent prepare for every missing prefix body, then writes the lock. A
Promise acknowledgement is never backed only by another signer's body pin.

`Manifest` receives a tolerant additive tail containing the complete
unresolved promise snapshot, including every body still required by a lock,
plus the journal position the snapshot reflects. Existing `write_manifest`
already syncs the journal before committing metadata, so the snapshot and
suffix have the same ordering discipline as app recovery. Boot loads the
manifest snapshot, replays later promise records idempotently, restores
bodies, constructs `PromiseGuard`, and only then starts PromiseNet or the
Simplex engine.

Journal pruning must retain either:

- the oldest record needed to reconstruct every unresolved lock; or
- a newer manifest that contains the complete unresolved snapshot.

A timer, circuit breaker, checkpoint, or process restart never erases a lock.
A matching canonical finalization releases it. An omitting canonical
finalization may release only a partial lock for which no `PromiseQC` could
have existed, as described below.

## The Cross-Protocol `PromiseGuard`

The `PromiseGuard` is shared by the Promise coordinator and
`ConsensusAutomaton`. It offers two mutually exclusive operations for a parent:

```text
install_lock(prefix):
    allowed only while Open
    journal + fsync first
    atomically publish the longer required prefix

authorize_canonical(payload):
    obtain payload bytes from ContentStore
    decode with existing decode_batch
    require every installed prefix at positions 0..k
    atomically close the parent to future Promise acknowledgements
    return true to Simplex only after the close
```

This closes the load-bearing race:

- if `install_lock` linearizes first, an omitting canonical payload is rejected;
- if `authorize_canonical` linearizes first, no later Promise acknowledgement
  can be released for that parent.

Closing the parent does not pin one canonical digest forever. After the first
authorization, later-view proposals remain admissible when they satisfy the
same required prefix; Promise signing simply stays closed. This preserves
ordinary Simplex reproposal and view-change liveness while keeping the race
one-way.

The assembler's seal path must call the same authorization operation before it
queues the canonical digest. Remote validators call it from the existing
`ConsensusAutomaton::verify` path after the current `ContentStore` availability
check. There is no second canonical validator.

The guard stores required ordered `FrameId`s, not certificate bytes. A
canonical proposal remains exactly the ordinary `encode_batch` payload. It
contains no `CanonicalBatchV2`, PromiseQC, bitmap, Merkle proof, or seal
sidecar. Consequently:

- execution and `OrderedNode::drain_delivered` are unchanged;
- the existing payload relay and resolver operate unchanged;
- explorers, state sync, recovery block replay, residents, and old clients see
  the current batch format; and
- promise evidence remains validator/client metadata instead of canonical app
  data.

On finalization, the existing reporter event and ordered drain reconcile the
ordinary batch against the guard. A matching successor records
`PromiseReleased`, demotes retained frame bodies, resolves receipts, and opens
eligibility only for the newly finalized parent. Any mismatch after a valid
`PromiseQC` is a fatal invariant violation, not an application rejection.

## View Change, Partial Locks, and Cutover

After the assembler loses its view, no validator signs new increments for that
session. The next Simplex proposer may query PromiseNet for signed recovery
summaries and should collect the longest valid chain before sealing. A quorum
of summaries necessarily intersects any PromiseQC quorum, but recovery is an
optimization rather than a new consensus prerequisite: lock holders enforce
safety even if the control plane is temporarily unavailable.

Every validator that installed a lock rejects an omitting proposal and sends a
signed `LockNack` containing the proposal and AvailabilityQC. One valid NACK is
enough for an honest proposer to fetch the bodies and repair its ordinary
batch. Unique availability subjects make all valid locks for an index part of
one chain; the proposer chooses the longest valid contiguous prefix.

A partial set of Promise acknowledgements can leave honest validators locked
without a client-valid `PromiseQC`. The lock is still enforced locally. If an
omitting canonical successor nevertheless finalizes, then under the `f`-fault
assumption a quorum PromiseQC could not have existed: a real PromiseQC would
contain enough honest lock holders to block that finalization. Recovery records
`PromiseReleased::NoQuorumSuperseded` and may clear the partial lock. A timer
alone may not.

Availability-only prepares are not promises. They may be released after the
guard authoritatively closes the parent without a lock.

PromiseNet attaches to the existing epoch barrier:

- an armed membership or binary cutover freezes new sessions early enough that
  their successor cannot be discarded at the view ceiling;
- an already binding lock must be matched by an old-epoch canonical successor
  before `respawn_if_due` may replace the engine;
- `BlockSink::cutover` and the respawn plan assert that no lock crosses into a
  different validator set; and
- PromiseNet transport, certificate suite, peer book, and guard are rebuilt
  or refreshed from the same new-epoch snapshot as Simplex. The long-lived
  plane may keep its sockets; it does not keep the old admission set or
  protocol session.

Accepted but unpromised frames continue to use the existing `outstanding`
cutover carry. A binding promise is never silently downgraded into ordinary
custody.

## Failure Behavior

| Failure | Receipt behavior | Canonical behavior |
|---|---|---|
| PromiseNet unavailable before any lock | no receipt | existing Simplex flush continues |
| candidate misses 100 ms target | no on-time receipt; metric records miss | later increment or ordinary flush |
| assembler equivocation | conflicting quorum certificates cannot both form | evidence retained; view may nullify |
| assembler dies before AvailabilityQC | no receipt | prepare releases on authoritative close |
| assembler dies after AvailabilityQC but before any lock | no receipt | ordinary successor may finalize |
| assembler dies after some Promise locks | no receipt unless `q` acknowledgements exist | NACK/recovery repairs; omission may prove partial lock superseded |
| assembler hides a completed PromiseQC | client receipt remains valid | locked honest validators enforce inclusion |
| promised body temporarily missing | receipt remains valid | signer-directed fetch; progress may halt |
| Promise data plane partition after lock | receipt remains valid | Simplex may halt until recovery communication returns |
| disk full before prepare/lock sync | validator does not attest; circuit opens | ordinary path continues only if no lock was installed |
| process crash | no new receipt while down | boot restores guard before voting |
| canonical proposal omits locked prefix | no receipt change | lock holders return false/NACK; proposal cannot finalize with a valid PromiseQC |
| epoch cutover becomes pending | no new session | existing cutover barrier and custody carry remain authoritative |
| more than `f` Byzantine validators | guarantee outside fault model | fail-stop evidence where detectable |

Fallback is intentionally asymmetric. Before a promise lock, Fastblocks may
disappear without affecting finality. After a lock, preserving the receipt is
more important than canonical liveness.

## Safety Argument

### Certificate uniqueness

Two quorums have an intersection of at least `2q - n = n - 2f`, which is
greater than `f` for the supported `N3f1` sets. Therefore their intersection
contains an honest validator. Durable anti-equivocation permits that validator
to attest to only one proposal for `(parent, session, index)`, so conflicting
AvailabilityQCs or PromiseQCs cannot both be valid.

Signer-set-independent proposal subjects ensure that two encodings of the same
valid certificate cannot create two prefix branches.

### Promise fulfillment

A valid PromiseQC contains `q` acknowledgements and therefore at least
`q - f = n - 2f` honest, durable lock holders. The remaining validators are
fewer than the `q` votes needed to finalize an omitting canonical successor.
Every honest lock holder authorizes only a batch beginning with the certified
prefix, so any successor that finalizes contains it.

### Cross-protocol race

For each honest validator, `install_lock` and `authorize_canonical` linearize
through one `PromiseGuard`. The former publishes only after durable storage;
the latter closes future promise signing before returning `true` to Simplex.
Thus an honest validator cannot contribute to both sides of an inclusion
violation even when PromiseNet and Simplex messages arrive concurrently.

### Data availability

Every Promise acknowledger holds and durably records the complete prefix, not
just a digest. A PromiseQC therefore leaves at least `n - 2f` honest body
holders. The new proposer can fetch by existing FrameId from lock holders; the
ordinary canonical payload then uses the existing content relay and resolver.

### Clock independence

Deadlines start and stop attempts but do not validate messages, clear locks,
choose signers, or alter subjects. Arbitrary clock skew can reduce liveness or
the number of fastblocks, not violate a receipt.

### Deterministic canonical execution

The final payload is the existing canonical batch encoding and enters the
existing single execution path. Fastblocks introduce no alternate app-state
transition, height, app hash, or commit order.

## Liveness and Performance Envelope

PromiseNet adds two validator message phases, body fan-out, frame validation,
certificate verification, two durable record barriers, and client
publication. A deployment cannot beat quorum RTT or storage latency.

The initial engineering budget per increment is:

| Stage | Target |
|---|---:|
| proposal and delta body reach a quorum | 25 ms |
| existing frame validation + durable prepare | 20 ms |
| availability attestations and certificate assembly | 15 ms |
| AvailabilityQC verification + durable lock | 20 ms |
| Promise acknowledgements, assembly, and publication | 15 ms |
| scheduler and queue slack | 5 ms |
| total | 100 ms |

These are acceptance budgets, not consensus constants or observed production
numbers. If quorum RTT or fsync consumes the envelope, operators increase the
period or leave Fastblocks disabled; they do not weaken the promise.

The launch gate is sustained operation at canonical capacity with:

- at least 99.9% of eligible windows producing a valid increment in the target
  deployment envelope;
- p95 PromiseQC formation at or below 100 ms and p99 at or below 150 ms;
- zero conflicting certificates, omitted receipts, or recovered-lock loss
  under the stated fault model;
- no material canonical-finality regression when PromiseNet is disabled or
  fails before a lock; and
- bounded memory, journal growth, queues, CPU, and boot recovery time under
  adversarial submissions.

The percentile and availability targets may change from measurements without
a wire upgrade. Quorum, lock, and receipt semantics may not.

## Client API and UX Reuse

The current client surfaces are extended instead of replaced:

- `NodeCommand::Submit` remains the single actor intake.
- `/v1/submit` keeps its current wait-for-finalization behavior by default, so
  existing callers and `SubmitReceipt` remain compatible.
- An additive wait preference may return after `received` or `preconfirmed`;
  every early response includes the stable `FrameId` and does not cancel
  custody when the caller times out.
- A `SubmissionStatus(FrameId)` actor command reads custody, an optional
  verified receipt, and final disposition.
- `StreamHub` adds a submission topic/update on the existing `/v1/stream`
  WebSocket. No second websocket or notification server is created.
- The existing `pending_submits` correlation map is keyed by the same
  `FrameId`; it publishes a preconfirmation update without consuming the
  holder that later resolves the existing final response.
- Resident submissions extend the existing submit-relay reply/status protocol
  with the same FrameId-keyed update; they do not acquire a direct PromiseNet
  vote or a second client gateway.

The transport-neutral progress object is:

```rust
struct SubmissionUpdateV1 {
    frame_id: FrameId,
    phase: SubmissionPhaseV1,
    receipt: Option<FastblockReceiptV1>,
    finalized: Option<SubmitReceipt>,
    rejection: Option<String>,
}
```

The app extends its existing `OpLedger` with one phase. Optimistic projection
remains a separate reversible presentation technique:

| State | Evidence | UI copy |
|---|---|---|
| `optimistic/pending` | local client projected an intent | **Sending…** |
| `received` | node accepted custody of the stable FrameId | **Queued** |
| `preconfirmed` | local node verified a portable `FastblockReceiptV1` | **Preconfirmed** |
| `finalized.applied` | canonical block and app hash | **Finalized** |
| `finalized.rejected` | canonical inclusion with deterministic rejection | **Finalized — rejected** |
| `carried` | existing cutover custody remains unresolved | **Carried to next epoch** |
| `preconfirmation_missed` | window ended without a receipt | stay **Queued**; optional fast-path detail |
| `unknown_after_timeout` | connection ended before an outcome | **Status unknown**; continue by FrameId |

The UI must never call the optimistic projection “preconfirmed,” show an
execution result from an inclusion receipt, or raise the existing finality /
read-your-writes floor on preconfirmation. Finalized refresh and app-hash
logic remain final-only.

The node verifies receipts using the same epoch certificate suite and exposes
only verified progress to the desktop. Portable SDK consumers may call the
pure verifier API and shared golden vectors; the desktop does not need a
second cryptographic implementation for its local-node path.

Recommended copy is: “Validators promised inclusion in the next finalized
block.” Detail text states that execution is pending and may still reject.

## Speculative Execution: Deferred

Base-like pending balances, reads, logs, and successful transaction receipts
require execution of the certified prefix against the parent state. That is
outside v1. Any future overlay must be disposable and keyed by the exact
parent/session/index/proposal, must never mutate canonical module state, must
quarantine irreversible effects, and must reconcile against final execution.

The v1 ordered prefix and receipt can support that later work, but this ADR
does not authorize speculative execution or pending-state RPC.

## Observability Reuse

New counters and histograms register in the existing node metrics registry.
Transport bytes, queue depth, and drops come from the existing data-plane
`StatsSnapshot`. Labels include network, epoch, role, protocol version, and
bounded outcome; raw FrameIds and transaction contents are not labels.

Required observations include:

- eligible/opened/closed windows and close reason;
- proposed, prepared, availability-certified, locked, promise-certified, and
  missed increments;
- custody-to-cut, proposal-to-AvailabilityQC, AvailabilityQC-to-lock,
  lock-to-PromiseQC, custody-to-receipt, and receipt-to-finality latency;
- existing batch bytes, promised bytes, unused capacity, deferred large
  frames, and overflow carry;
- control/body queue depth, per-peer RTT, throughput, retransmit, and dropped
  hints;
- frame validation, journal sync, certificate verification, and assembly time;
- rejected messages by bounded reason, equivocation, replay, and bad proofs;
- recovery summaries, NACKs, restored locks, missing bodies, and repair time;
- circuit-breaker state and disk reservation; and
- canonical finalization latency with Fastblocks active, inactive, and failed
  before/after a lock.

Any valid receipt omitted or reordered by its canonical successor is a
page-level invariant violation. Forensics retain the receipt chain, epoch
participant set, recovered promise records, and ordinary canonical batch.

## Security and Abuse Resistance

| Threat | Required defense and reused owner |
|---|---|
| forged receipt | epoch certificate suite, separate domain, Commonware quorum verification |
| cross-protocol signature replay | distinct Fastblock subjects/namespaces bound to network, epoch, parent, and role |
| assembler equivocation | durable one-vote key, quorum intersection, evidence counter |
| body withholding | prepare-before-attest, Promise acknowledger retention, FrameId fetch |
| certificate withholding | post-lock PromiseQC semantics, broadcast, recovery summaries |
| resident pretending to vote | validator-only epoch admission plus certificate participant check |
| datagram spoof/loss | WireGuard attribution, signed subjects, stream retry |
| malformed or oversized frame flood | existing cap and decoder before durability; bounded queues |
| certificate / proof allocation bomb | bounded codec configs before allocation |
| cached body eviction | promised bodies enter pinned retention and Recovery |
| disk exhaustion | one-batch cap, reserved journal budget, no attestation after write failure |
| signature CPU exhaustion | admission before crypto, duplicate cache, bounded batch verification |
| stale assembler | authoritative Simplex callback/activity, not a timer claim |
| promise/canonical race | shared `PromiseGuard` linearization |
| lock loss on restart | existing Recovery journal + manifest replay before engine start |
| cutover drops a promise | existing epoch barrier extended with unresolved-lock assertion |
| old validator votes for omission | height-gated `R = n` activation |
| misleading UX | receipt-gated `preconfirmed`; final-only execution/result language |

Equivocation evidence may inform operator policy or future slashing. v1 does
not add an on-chain slashing rule, and safety never depends on punishment.

## Compatibility and Activation

The canonical application payload does **not** change. Residents, followers,
state-sync consumers, explorers, module execution, and old clients continue to
consume ordinary batches. Receipt-aware API changes are additive.

Validator behavior is still consensus-sensitive: an old validator does not
restore Promise locks or reject an omitting batch. Binding mode therefore
activates only through the existing height-gated upgrade mechanism with
**`R = n` readiness**:

1. every current validator runs a binary that understands Promise wire
   objects, the epoch certificate scheme, new recovery record tags, and the
   guard;
2. the existing upgrade module collects readiness from the live boundary
   validator set and arms one activation height;
3. nodes may pre-open `Service::Promise` in dark mode but emit no binding
   acknowledgements before activation;
4. the existing cutover freeze prevents a session from straddling the
   boundary;
5. epoch respawn constructs Simplex, PromiseNet, the participant book, and the
   certificate suite from one agreed snapshot; and
6. the active protocol version enables promise signing and canonical guard
   enforcement together.

No new feature-negotiation consensus is added. Diagnostic capability fields
may expose support, but the committed upgrade state is authoritative.

Rollback before activation is ordinary binary rollback. A binary used after
activation must continue to decode and honor unresolved promise records even
if its fast path is disabled. Downgrading to a binary that treats new recovery
tags as unknown or ignores locks is unsafe and requires another coordinated
upgrade/migration.

## Verification Strategy

### Reuse regression gates

- Golden tests prove the extracted `BatchBuilder` emits byte-identical batches
  to current `flush_batch`, including capacity boundaries and the single-frame
  exception.
- With Fastblocks disabled, canonical digests, drained member order, app hashes,
  recovery replay, cutover carry, HTTP final receipts, and OpLedger transitions
  remain unchanged.
- Promise body intake and restart seed the same `ContentStore` keys as
  `frame_id` / `digest_of`.
- The generic epoch overlay book preserves statesync behavior while enforcing
  validator-only Promise admission.
- Both `V1Ed25519` and `V2Bls` use the same participant ordering and Commonware
  certificate verifier as their Simplex epoch.

### Pure protocol and property tests

- canonical subject encoding, domain separation, receipt Merkle roots/proofs,
  malformed codecs, and bounded-decoder vectors;
- `N3f1` arithmetic across every supported validator count, delegated to and
  cross-checked with Commonware;
- conflicting AvailabilityQCs and PromiseQCs cannot both assemble;
- certificate signer-subset variation never changes proposal-chain identity;
- prefix append-only, reservation order, deduplication, capacity monotonicity,
  and ordinary-batch equivalence;
- generated interleavings of `install_lock` and `authorize_canonical` admit no
  double authorization;
- crash at every prepare/lock/release append and sync boundary;
- manifest snapshot plus journal suffix replay is idempotent; and
- receipt rejection for wrong network, epoch, parent, view, frame, position,
  proof, scheme, or participant set.

### Deterministic BFT simulation

- one, four, seven, and non-`3f + 1` validator counts supported by `N3f1`;
- ten attempted increments per one-second window;
- reorder, duplicate, drop, delay, and partition every Promise message class;
- Byzantine assembler equivocation, withholding, and death before/after each
  durable boundary;
- up to `f` validators double-signing, silent, slow, or serving corrupt bodies;
- multiple Simplex nullifications and view changes with no lock, a partial
  lock, and a valid hidden PromiseQC;
- partial-lock omission finalization proves no PromiseQC and releases safely;
- real PromiseQC makes every omitting finalization schedule impossible;
- recovery summary selection and NACK repair converge without Byzantine help;
- circuit break before a lock preserves ordinary Simplex liveness;
- restart and checkpoint pruning never erase an unresolved lock; and
- membership and binary cutover never accept or carry a binding old-epoch
  promise.

### Integration and performance

- real `OverlaySockets` with isolated control/body flows and forced datagram
  loss;
- slow/full disk, corrupt journal tail, process kill, and restart;
- submit through validator and resident paths, including forwarding to an
  elected assembler and progress propagation back;
- one-MiB-class frames, many small frames, duplicate floods, and overflow;
- intended validator geography under p50/p95/p99 RTT, jitter, loss, bandwidth,
  and fsync distributions;
- 24-hour canonical-capacity soak against latency and resource gates; and
- desktop tests for optimistic, queued, preconfirmed, finalized, rejected,
  carried, missed, and unknown states.

Production enablement requires the simulator to continuously assert: every
emitted valid receipt is fulfilled, or canonical progress safely stops.

## Rollout

### Phase 0 — extract reusable seams

Extract `BatchBuilder`, `BlockCadence`, the service-parameterized epoch peer
book, and scheme factory without enabling Fastblocks. Land byte-for-byte and
behavioral regression tests first.

### Phase 1 — dark PromiseNet

Append `Service::Promise`, construct the isolated plane from the existing
epoch lifecycle, and exercise bounded control/body flows, admission, stats,
and fault injection. Shadow assemblers preview the existing FIFO but create no
durable lock or client state.

### Phase 2 — shadow certificates and recovery

Add Fastblock subjects, both epoch scheme variants, prepare records, receipt
verification, simulator, and recovery replay. Validators may assemble
non-binding shadow AvailabilityQCs and compare the predicted prefix with the
ordinary finalized batch. No Promise acknowledgement or `preconfirmed` UI is
enabled.

### Phase 3 — binding protocol behind activation

Add durable locks, `PromiseGuard`, NACK/recovery, release records, and the
cutover barrier. Exercise the existing `R = n` height-gated activation on
disposable and canary networks. Keep receipt access operator-only until safety
and latency gates pass.

### Phase 4 — inclusion-preconfirmation UX

Extend existing submit/status/stream surfaces and `OpLedger`, enable verified
receipts for canary users, and measure custody-to-receipt separately from
receipt-to-finality. Expand only after invariant and SLO gates remain green.

### Phase 5 — default fast UX

Enable inclusion preconfirmation by default for compatible networks while
preserving the existing final-only API default and circuit breaker.

### Separate ADR — speculative state

Pending reads, execution receipts, logs, effect quarantine, and reconciliation
are not implied by this rollout.

## Consequences

### Benefits

- Users receive quorum-backed inclusion feedback in roughly 100–200 ms in the
  target deployment envelope.
- The promise survives ordinary assembler failure and is stronger than a
  sequencer, ingress-node, or RPC acknowledgement.
- The final block remains byte-for-byte compatible with Ducktape's current
  canonical batch and execution path.
- Existing leader election, custody, packing, content resolution, recovery,
  epoch membership, upgrade, API, metrics, and UI state owners remain the
  source of truth.
- Scheme reuse automatically preserves Ed25519 and BLS epoch compatibility
  without a Fastblocks-only signature format.
- The small `PromiseGuard` makes the only cross-protocol race explicit and
  independently model-checkable.
- Disabled and pre-lock failure paths remain ordinary Simplex.

### Costs and trade-offs

- Two quorum phases and two durable barriers per increment are expensive.
- The 100 ms target constrains validator placement, disk latency, and control
  queue scheduling.
- Binding locks intentionally couple an off-consensus protocol to the existing
  consensus verifier at one audited boundary.
- A real promise may halt canonical progress until its bytes are recovered;
  that is the cost of making the promise meaningful.
- Recovery records, manifest snapshots, receipt evidence, and frame pins add
  disk and forensic-retention pressure.
- The `OrderedNode` batch helper and automaton/reporter acquire new extension
  seams even though their disabled behavior stays unchanged.
- v1 permits only one promise session per parent; a failed assembler can remove
  fast UX for that boundary.
- v1 promises inclusion only. It does not provide Base-like pending state or
  successful execution receipts.

## Alternatives Considered

### Keep only local optimistic UI

Useful and retained, but it is not evidence of network custody, order, or
future inclusion. Rejected as the meaning of preconfirmation.

### Accept one validator or assembler acknowledgement

A single signer may fail, equivocate, or lose proposer authority. Its
statement cannot constrain a later BFT quorum. Rejected.

### Copy Base's sequencer Flashblocks directly

Incremental construction and cumulative capacity are useful patterns. A
single active-sequencer trust model is not equivalent to Ducktape's validator
finality model. Rejected; the assembler coordinates but a quorum promises.

### Add `CanonicalBatchV2` and a certificate sidecar

Embedding Promise evidence would version every canonical consumer, consume
payload headroom, duplicate data already enforced by lock holders, and couple
execution/recovery to a UX proof. The existing batch plus validator-local
guard is sufficient for safety. Rejected.

### Build a standalone Fastblocks crate, mempool, CAS, WAL, and RPC service

This duplicates ownership and creates reconciliation problems at every seam.
The protocol logic fits as small modules/facets of the existing node,
consensus, and recovery owners. Rejected unless future dependency constraints
prove a minimal shared types crate unavoidable.

### Reuse the statesync plane instance or its service ID

It would couple bulk state transfer to latency-critical promise control and
broaden admission from validators to the transport set. Rejected. The plane
implementation and peer-book pattern are reused; the instance, service ID,
queues, and policy remain isolated.

### Hard-code Ed25519 Fastblock certificates

Ducktape already supports epoch-selected Ed25519 and BLS consensus schemes.
A second certificate format would drift in participant order, bitmap, codec,
and upgrade behavior. Rejected in favor of a subject adapter over the existing
Commonware certificate primitive.

### One-phase availability certificate

A Byzantine assembler could reveal a completed certificate only to a client
before honest validators durably install a canonical constraint. Rejected in
favor of availability followed by post-lock Promise acknowledgements.

### Independent leaderless validator lanes

They leave canonical merge order, duplicates, conflicts, capacity, and receipt
semantics unresolved and evolve into another DAG/mempool consensus protocol.
Rejected for v1.

### Run a second BFT consensus every 100 ms

This creates a second replicated log with its own view change, recovery, and
canonical reconciliation. It is much larger than an inclusion promise.
Rejected.

### Shorten canonical block time to 100 ms

This multiplies Simplex rounds, app commits, heights, checkpoints, and module
overhead by ten and still cannot beat quorum physics. Rejected.

### Preconfirm successful execution in v1

This requires deterministic speculative state and effect quarantine. Ordered
inclusion captures the primary latency signal with a smaller integrity
boundary. Deferred.

## Implementation Boundaries

No new binary, database, canonical codec, or standalone kernel crate is
planned for v1.

| Existing location | Change |
|---|---|
| `crates/kernel/node` | extract `BatchBuilder`; add idempotent FrameId reservation; define the canonical-prefix `PromiseGuard` and `PromiseSafetySink` interface |
| `crates/kernel/consensus` | add `fastblocks` subject/certificate/state-machine module; extend automaton/reporter with authoritative lifecycle and guard checks; reuse `ContentStore`, scheme construction, and `N3f1` |
| `crates/kernel/recovery` | implement `PromiseSafetySink` in the existing journal; add tolerant record/manifest tails and recovered lock/body output |
| `crates/system/data-plane` | append `Service::Promise = 5` and ports only; reuse all plane/flow/stats machinery |
| `bin/node` | wire the per-use plane, generic epoch peer book, node-actor coordinator, forwarding, cut/seal cadence, cutover barrier, circuit breaker, and metrics |
| `bin/noded` | extend existing command/status and stream surfaces; preserve default finalized submit behavior |
| `app` | add evidence-gated `preconfirmed` to `OpLedger`; keep optimistic projection and finality floor separate |

Dependency direction remains intact: `node` owns frame/batch invariants;
`consensus` may depend on them; `recovery` implements node's persistence
interface without importing consensus internals. Promise certificates are
stored as bounded opaque canonical bytes where recovery does not need to
interpret them. If portable Rust consumers later require a shared protocol
types crate, that extraction must preserve these ownership boundaries and is
not a license to duplicate runtime state.

Each rollout phase is independently mergeable and must leave the disabled
ordinary path green.

## Deferred Decisions

These require measurement or separate ADRs and do not change v1 safety:

- exact bounded queue sizes, retry intervals, body chunk size, and disk reserve;
- whether datagram hints improve p99 enough to retain;
- fee/priority selection among frames not yet reserved;
- changing the 100 ms target for wider validator geography;
- weighted validator sets, coordinated with the Simplex quorum model;
- economic slashing for signed equivocation or unavailable promised data;
- multiple safe assembler sessions for one parent; and
- speculative execution and pending-state RPC.
